# 03 - 课程与视频 API（course + vod）

> 本文档覆盖路由前缀 `/api/v1/course/**`（课程、章节、课时、图文资料）与 `/api/v1/vod/**`（上传凭证、媒资、转码事件消费、播放凭证、解密密钥、心跳上报、进度查询）。
>
> **课程与视频的授权（下发给某个节点/学员）不在本分册**：课程（`resource_type=1`）与视频（`resource_type=3`）统一走 `/api/v1/org/**` 的资源授权接口（表 `org_resource_grant`），由 03-02《组织机构》分册定义。本分册只定义资源本身的管理与消费，以及"我是否被授权"的判定口径。
>
> 通用约定（认证方式、响应结构、分页、时间格式、错误码总表）见 `00-通用约定.md`；本文档所有表名、字段名、枚举值、路由前缀均以 `DESIGN-CONTRACT.md` 为唯一权威。

## 0. 模块级通用说明

### 0.1 认证与多租户

- **本分册所有接口均需请求头** `Authorization: Bearer {accessToken}`（Sa-Token JWT）。<br>原先第 29 号「获取解密密钥」是唯一的例外（免登录、身份来自 URL 上的 `MtsHlsUriToken`），**该接口已随加密路线改为阿里云私有加密而删除**（§8.2 墓碑小节）——**本分册从此没有免登录接口**，`00-通用约定` §2.3 的白名单也由四条减为三条。
- 所有业务数据按 `tenant_id` 自动隔离（MyBatis-Plus 租户插件注入）；**跨租户访问一律返回 HTTP 404**，不暴露资源存在性（契约 2.1）。
- 所有雪花 ID（bigint）在 JSON 中一律序列化为**字符串**；时间格式统一 `yyyy-MM-dd HH:mm:ss`（东八区）。
- `DELETE` 方法一律为逻辑删除（后端逻辑删除（`deleted_at` 写入毫秒时间戳），契约 6.1）；`vod_heartbeat_log` 等日志明细表除外（契约 2.2）。
- 分页接口统一请求参数 `pageNum`（默认 1）、`pageSize`（默认 10，最大 100），响应统一 `data: {"total": 100, "list": [...]}`。

### 0.2 角色、数据权限与资源可见性（对齐契约 §2.3 / §2.4 / §2.5）

**两条彼此独立的判定必须同时满足**：

1. **数据权限（看到哪些行）——全系统唯一一条规则（契约 §2.4）**：你能看到的数据 = 你所在节点的子树。
   ```sql
   -- org_node 别名 n，当前用户所在节点 #{myNodeId}
   n.id = #{myNodeId} OR FIND_IN_SET(#{myNodeId}, n.ancestors) <sup>⚠ 语义表达，执行写法见契约 §2.4 子树查询选路表</sup>
   ```
2. **资源可见性（能用哪些课程/视频）——逐级显式授权，无继承（契约 §2.5）**：

   > **可见 = 我的节点就是该资源的 `owner_node_id`，或该资源已被显式授权给我的节点（`org_resource_grant` 命中且当前时间在有效期内）。**

   ```sql
   -- 课程可见性判定（resource_type=1；视频同理取 3）
   c.owner_node_id = #{myNodeId}
   OR EXISTS (
       SELECT 1 FROM org_resource_grant g
        WHERE g.resource_type = 1
          AND g.resource_id   = c.id
          AND g.target_node_id = #{myNodeId}          -- 精确等于我的节点
          AND g.deleted_at = 0
          AND (g.valid_start IS NULL OR g.valid_start <= NOW())
          AND (g.valid_end   IS NULL OR g.valid_end   >= NOW())
   )
   ```

   - **不回溯祖先链、无继承**：判定只看 `target_node_id = 我的节点` 这一条命中，**绝不**用 `FIND_IN_SET` 去匹配我的任一祖先节点。上级拥有 ≠ 我自动拥有；父级授权给了我的下级也不等于授权给了我。 <sup>⚠ 语义表达，执行写法见契约 §2.4 子树查询选路表</sup>
   - **不做向下展开**：我拥有某课程，不代表我的子节点自动可用；子节点必须被显式授权（由 03-02 的授权接口逐级下发）。
   - 授权过期（`valid_end` 已过）等同未授权：列表不返回，单条访问返回 20013（学生端消费场景）。
   - 授权被撤销时按契约 §2.5 规则 5 **级联撤销目标节点整棵子树**上的同一资源授权；已产生的 `vod_watch_progress` 一律保留，仅失去继续访问权。

| 角色 | role_key | 数据范围（子树） | 本模块资源范围与权限概览 |
| --- | --- | --- | --- |
| 管理员（机构/下级，同一角色） | `org_admin` | 其节点子树全部 | 管理端全部接口；课程/媒资范围 = 本节点 `owner_node_id` 的 + 被显式授权给本节点的 |
| 教师 / 导师 | `teacher` | 其子树 = 名下学员 | 管理端接口：可管理 `owner_node_id` 为本人教师节点的课程、章节、课时、资料、媒资（**但不能上传视频** —— 接口 25 需方 2026-08-21 定案二收窄为仅 `org_admin`；`vod:video:` 的 list / remove / retranscode / status 四项不变）；对"被授权给本人节点"的课程为**只读可用**（可预览、可再下发给名下学员，下发走 03-02），不可编辑或删除 |
| 学生 | `student` | 仅自身 | 学生端与播放接口：仅可访问**显式授权给本学生节点**且在有效期内、且课程已上架的课程；进度数据仅本人 |

- **只读可用 vs 可编辑**：编辑/删除/上下架类写操作要求 `owner_node_id = 我的节点`（仅被授权者不可写，返回 403）；查询与消费类操作按上文资源可见性判定。
- 平台超管（`super_admin`）不参与本模块业务操作。
- 各接口「权限」栏在此基础上给出具体说明。

### 0.2.1 课程与视频的归属字段

- `crs_course.owner_node_id`、`vod_video.owner_node_id`：**创建时写入创建者所在节点**（`sys_user.node_id`），此后不随创建人调岗自动变更；节点被移动时资源随节点走（归属仍是该节点）。
- 响应中统一以 `ownerNodeId` / `ownerNodeName` 暴露；`ownerNodeId` 为 bigint 字符串。
- **归属唯一真相源**：课程/媒资的归属只有 `owner_node_id` 一个字段。原 `crs_course.teacher_id` 与 API 中的 `teacherId` / `teacherName` **已彻底移除**（避免归属存在两个真相源）——展示「这是谁的课」一律用 `ownerNodeId` / `ownerNodeName`；需要作者署名时用通用字段 `createBy` / `createByName`（`sys_user`）。

### 0.4 API 字段与契约表字段映射说明

- API 中 `videoId` 对应 `crs_lesson.video_id`（→ `vod_video.id`）。
- API 中 `materialId` 对应 `crs_lesson.content_id`（→ `crs_material.id`，契约字段名为 `content_id`，API 层为语义清晰使用 materialId，开发实现时按此映射，不新增表字段）。
- API 中 `coverUrl` 为服务端根据 `cover_file_id` **现签**的展示字段，非表字段。**「计算」= 调 `FileService#inlineSignedUrl(coverFileId)` 拿对象键签一个 ≤30 分钟的内联地址**，不是把 `sys_file.file_url` 读出来直接返回——该列**只存对象键**，直接下发等于给出一条永久直链（`00-通用约定` §7.4 第 1 行、D-2 定案）。本地存储模式下签不出地址，`coverUrl` 为 `null`；生产一律 OSS。

## 1. 课程管理（管理端）

### 1.1 课程分页列表

- **方法+路径**：`GET /api/v1/course/courses`
- **权限**：`org_admin`、`teacher`
- **数据权限（0.2 资源可见性）**：返回 **`owner_node_id` = 我的节点** 的课程 ∪ **已显式授权给我的节点且在有效期内**（`org_resource_grant`，`resource_type=1`）的课程。**不回溯祖先链、无继承**——上级节点拥有的课程若未显式授权给我，本接口不返回。响应逐行以 `grantType` 标识来源（1 自有 2 被授权）。

**请求参数（Query）**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| pageNum | integer | 否 | 页码，默认 1 |
| pageSize | integer | 否 | 每页条数，默认 10，最大 100 |
| courseName | string | 否 | 课程名称，模糊匹配 |
| subject | string | 否 | 科目，精确匹配 |
| status | integer | 否 | 课程状态：0 草稿 1 已上架 2 已下架 |
| grantType | integer | 否 | 来源筛选：1 仅自有（`owner_node_id`=我的节点）2 仅被授权；不传返回两者并集 |

**请求示例**

```
GET /api/v1/course/courses?pageNum=1&pageSize=10&courseName=数学&status=1
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

{

  "data": {
    "total": 1,
    "list": [
      {

        "courseName": "高一数学（必修一）",
        "coverFileId": "1949600000000000021",
        "coverUrl": "https://cdn.edumatrix.cn/cover/math1.jpg",
        "subject": "数学",
        "ownerNodeId": "1952000000000000301",
        "ownerNodeName": "王建国（导师）",

**响应字段说明**：`grantType` 1 自有（`owner_node_id` = 我的节点）/ 2 被授权（`org_resource_grant` 命中）；`grantedNodeCount` 为该课程当前有效授权的目标节点数（仅 `grantType=1` 的行返回真实值，被授权行返回 `null`——**下级不得窥探同级/上级的授权面**）。

**相关业务错误码**：无（仅通用 400/401/403）。

> **〔本条由需方定案推翻原措辞，F-42〕** 原文把「课程不存在」写作 `20004`，而「存在但对我不可见」是 HTTP 404 —— 两条各自都对，**合起来却能被拿来探测存在性**：拿到 `20004` = 这个 id 在本租户不存在，拿到 404 = **存在但你看不到**。而 `03-01 §7.2` 恰恰用「雪花 ID 同租户内时间相邻、可近邻枚举」论证过详情接口不能下发直链。**统一到 404**，不是统一到业务码 —— 契约 §2.4 三分法第 1 行「访问**路径上的资源**而该资源不在我的子树内 → **404**，不暴露存在性」是上位文档、动不得，能动的只有「不存在」那一侧。
>
> **`20004` 没有退役**：它<b>只</b>用于**请求体 / 查询参数里显式指定的 `courseId`**（§2.2 创建章节的 body、§3.1 课时列表的 query）——那一类用户主动选了对象，选错了要明确提示，返 404 会指代不清（契约 §2.4 三分法第 3 行同一条理由）。**同一形状的 `20009`（§4）与 `20014`（§3）一并改**，章节本来就是全 404，是本轮的参照物。

### 2.5 章节拖拽排序

- **方法+路径**：`PUT /api/v1/course/courses/{id}/chapters/sort`

- **业务规则**：
  1. `chapterId` 必须存在、未删除、且属于目标课程，否则返回 **`20007`**；`course_id` 由服务端根据章节自动冗余写入。
  2. `lessonType=1`（视频）：`videoId` 必填（缺失返回 20019），且对应 `vod_video` 必须存在、未删除，否则返回 20008；**当本次目标 `status=1`（可见）时，还要求该视频 `status=2`（正常），否则返回 20008**；`duration` 由服务端冗余自 `vod_video.duration`，请求中不接受。
     > **〔本条由需方定案推翻原措辞，依据 PRD F2-1 规则 4 与验收标准可达性〕** 原文是「对应 `vod_video` 必须存在、未删除、`status=2`，否则返回 20008」，即**任何**创建/修改都卡。按权威顺序（`DESIGN-CONTRACT` > 03 六分册 > `01-PRD`）本该以本分册为准，需方仍选择了 PRD F2-1 规则 4 的口径（「……才允许将课时**置为 `status=1` 可见**」），理由是：卡在创建这一步会让 PRD F2-1 那条验收标准「关联视频 `status=1`（转码中）时将课时状态改为可见 → `20008`」**几乎走不到**——课时根本建不出来，等于把一条验收标准做死。**上架校验（§1.6 规则 2）保留为第二道网。** 已登记 F-43。

  4. 创建/修改/删除课时后，服务端在**同一事务内全量重算** `crs_course.lesson_count` 与 `total_duration` 冗余值。
     > **〔订正：原文为「异步重算」，与同一分册 §2.4「同步维护」自相矛盾〕** 取同事务：异步任务失败会让冗余值与真实值不一致，而**接口返回 200、字段齐全、数字是错的**，且该不一致在请求内无法验证。重算是全量 `COUNT` / `SUM`（不是增量 ±1），漏一次也会在下一次课时变更时自愈。

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| chapterId | string | 是 | 所属章节 ID（章或节，推荐节） |
| lessonName | string | 是 | 课时名称，1~100 字符 |

### 7.2 转码事件消费（XXL-Job 任务，非接口）

> **本节不是接口，是一个定时任务**，因此不出现在接口目录中。它取代了原先的 `POST /api/v1/vod/callback/{provider}` 免登录回调端点——改造理由见本节末「为什么不用 HTTP 回调」。

- **形态**：XXL-Job 每 10s 触发一次，主动向阿里云**轻量消息队列（原 MNS）**拉取转码事件并消费。**拉模式，无入站端点**：不需要新进程、不需要公网端口、不需要网关放行。
- **鉴权**：消费方以 **AK/SK** 访问队列，**无需签名校验**——身份由云 SDK 承担，天然免疫伪造与重放。
- **租户上下文**：本任务属契约 §2.8 的第二类（调度器触发、无用户会话），三条规则原样适用：从 `vod_file_id` 反查媒资行取 `tenant_id` → `TenantHelper.setTenantId()` → 处理完 `clear()`；跨租户消息按租户分片处理；反查不到租户一律拒绝并告警。

**事件映射**

| 内部事件 | **阿里云事件** | 处理动作 |
| --- | --- | --- |
| 上传完成 | `FileUploadComplete` | `status` 0→1（转码中）。阿里云路径下 `vod_file_id` 在**发上传凭证时**即已写入（`cloudVideoId`），此处只推进状态 |
| 转码成功 | **`TranscodeComplete`（`Status=success`）** | `status` 1→2（正常）。**不采信报文中的任何 URL**（理由见下），改为反调 `GetPlayInfo` 取播放地址，从中按 `Format == "m3u8" && Encrypt == true` 挑出唯一一路写入 `hls_url`；`duration` 取该路 `Duration`（浮点秒，`ceil` 取整）、`size_bytes` 取 `Size`。**挑不到则置 `status=3` 并告警，不得置 2**。<br>**〔登记（F-56）：`cover_url` 的回填在本表与 `PRD F2-3` 规则 1 之间不一致〕** PRD 写它由本事件回填，本表没有它。且实测 `GetPlayInfo` 的 `VideoBase.CoverURL` 是 `http://…?Expires=…&Signature=…`（既是混合内容又带时效签名，而同一响应里 `PlayURL` 是 `https://`）——**本轮不回填，列保持 NULL**，口径待定 |
| 转码失败 | **`TranscodeComplete`（`Status=fail`）** | `status` 1→3（转码失败），失败原因（`ErrorCode` / `ErrorMessage`）写入 `remark` |

> **转码成功必须映射 `TranscodeComplete`，不能映射 `StreamTranscodeComplete`**——后者是**单个清晰度**转码完成。一个视频配两档模板就会收到 2 条，每条各带自己那一路的 `FileUrl` / `Duration` / `Size`。若按它跃迁状态：低清那路先转完即置 `status=2`、`hls_url` 写成低清那一路，课时随即通过可见性校验（`20008` 要求 `status=2`）可以上架；而第 2 条因幂等键相同被丢弃，高清地址永远写不进去。
>
> **另有一条不能只订阅单清晰度事件的理由**：源视频损坏导致所有流都失败时，失败回调走的是 `TranscodeComplete`；只订阅 `StreamTranscodeComplete` 会**收不到任何失败通知**，媒资永远卡在"转码中"。
>
> `StreamTranscodeComplete` 可订阅用于观测各清晰度进度，但**不得用于状态跃迁**。
>
> **转码模板组只允许配单档**（契约 §1 部署约定）：`hls_url` 是单值列，配多档会让学生实际观看的清晰度由挑选规则决定、不可控。
>
> **挑选条件为 `Format == "m3u8"`——加不加密都收（F-114 第二半改）。** 原文是 `Format == "m3u8" && Encrypt == true`，
> 那一条把「模板组配的是加密输出」这个假设写进了代码：需方换成不加密模板后，转码成功的视频会被我们判成 `status=3`。
> **加密与否改为落库时按实际观测值记**（`vod_video.encrypt_type`），不再是准入条件。
> 原文「误配成未加密 MP4 时会挑出空集」的担心由 `Format == "m3u8"` 这一半承担，仍然成立。

**为什么不采信报文里的 URL**

阿里云官方明确：**回调 body 中返回的 URL 均为 HTTP 地址，暂不支持返回 HTTPS**。而本系统 00-通用约定 §1 与 PRD 7.3 都要求全站 HTTPS，学生端是 `https` 页面——把 `http://xxx.m3u8` 存进 `hls_url` 会被浏览器按**混合内容（mixed content）直接拦截**，播放失败，且控制台报错与业务无关，排查时会先怀疑密钥接口。

因此统一约定：**事件只当作"状态推进信号"，播放地址一律反调 `GetPlayInfo` 获取**。这条同时满足两个要求——防伪造（报文内容不参与写库）与 HTTPS。

**消费流程与顺序约束**

```
拉取一批消息（单次上限 16 条）
  → 逐条：解析 vod_file_id → 反查 vod_video 取 tenant_id
        → TenantHelper.setTenantId(tenantId)
        → 幂等判定：vod_file_id + EventType + Status 已处理过则跳过
        → 反调 GetPlayInfo 取播放地址 → 落库（状态 + hls_url + duration + size_bytes）
        → **落库成功后才删除消息**
        → TenantHelper.clear()
  → 冗余刷新（引用该视频的课时 duration、所属课程 total_duration）**另发一个异步任务**，不放在本事务里
```

- **幂等是必需项，不是优化**：轻量消息队列是 **at-least-once**，消息被消费后仅在一段时间内不可见，**必须主动删除**，否则会被再次消费。幂等键 `vod_file_id + EventType + Status`——加 `Status` 是因为 `TranscodeComplete` 的成功与失败共用同一 `EventType`，只用前两段会把"先失败重试后成功"的第二条误判为重复而丢弃。
- **必须先落库成功再删消息，顺序反了就是丢事件**。删了消息而落库失败，这条转码完成事件就永久消失，媒资卡在 `status=1`。
- **不可见时长（visibility timeout）必须大于单条消息处理耗时上限**，否则处理还没完消息就重新可见、被下一轮拉取重复消费。该值与 XXL-Job 拉取间隔要一起定。
- **冗余刷新必须异步**：一个视频可被 N 个课时引用（`idx_video_id` 正是为此反查而建），每个课时又要回写所属课程的 `total_duration`。把这串扇出放进消费事务会显著拉长单条消息的处理时间，进而逼高不可见时长。
- **反查不到媒资时**：记 `sys_oper_log` + `vod_callback_orphan_total` 指标，**并删除该消息**——否则它会被无限重投。这与契约 §2.8 规则 3「无法确定租户的写入一律拒绝并告警」一致：拒绝写入，但要让人看见。

**为什么不用 HTTP 回调**

| | HTTP 回调 | **SMQ 拉取（本方案）** |
| --- | --- | --- |
| 身份校验 | 机制不确定，可能只有密钥参数 + IP 白名单 | AK/SK，免疫伪造与重放 |
| 投递可靠性 | 官方明确"**忽略响应包体，仅以 HTTP 状态码为准**"，业务码 200 会被判成功 | 消息留在队列，不删除即自动重投 |
| 处理耗时 | **5 秒硬超时**，超时即判失败 | 拉取方自控节奏，无超时约束 |
| 公网入口 | 需要一个免登录公网端点 + 网关 IP 白名单 | 不需要任何入站端点 |

第三行是本项目的直接杀手：转码成功要写 `hls_url` / `duration` / `size_bytes`，还要刷新 N 个课时的 `duration` 冗余与各自课程的 `total_duration`，再加租户上下文设置与埋点——主库一抖动就破 5 秒，云端判失败重投，幂等键拦下，三次后放弃。**结果是转码成功了但状态没推进，媒资卡在 `status=1`，而日志里看起来一切正常。**

第四行对本系统尤其值钱：原回调端点是全部免登录接口里**唯一一个接受任意外部 POST 并据此写库**的。去掉后白名单只剩登录、验证码、刷新令牌与解密密钥四条——前三条不写业务表，第四条是只读且被 `MtsHlsUriToken` 限定到单个学生与单个课时。**再没有一个免登录入口能写库。**<br>**〔本轮再减一条〕** 解密密钥接口已随加密路线改为阿里云私有加密而删除（F-112），**白名单现为三条、且全部属于认证自身，系统里没有任何免登录的业务接口** —— 上面那句「再没有一个免登录入口能写库」从此可以说得更强：**连读都没有了**。

**新增的失败模式（必须监控）**：点播服务写队列失败时会重试 2 次、共 3 次，超过后**丢弃**。三种成因——未授权访问、Endpoint 非公网、队列名不对——**全是配置错误，不是运行时抖动**。也就是说配对了就不会因为我们的服务挂掉而丢消息（写入与消费解耦），但**配错的后果是静默丢弃**。故必须有"队列长时间无消息"的探活指标（契约 §7.1 `vod_event_last_consume_lag_seconds`）。

## 8. 播放与防刷（重点）

> 设计目标（对齐原始需求模块 2）：加密 HLS + 时效播放凭证防盗链；~~**禁用向前拖拽**（仅允许回看已看部分）~~ **→ F-113 取消，拖拽完全放开**；**跑马灯水印**（姓名 + 手机号）防录屏传播；**心跳上报 + 前端计时器**记录观看时长；高频写走 Redis 缓冲异步落盘（原始需求第四节）。
>
> **⚠ F-113 后本章不再以"防刷"为设计目标**（需方定案「刷课不需要防」）。保留下来的校验规则**大多换了理由**——留痕、诊断、兜 bug，逐条见 §8.3.1。

### 8.1 获取播放凭证

> **⚠ 本节已按加密路线改写（F-112）**：加密方式为**阿里云私有加密**（`AliyunVoDEncryption`），播放走 **`VidAuth`**（`GetVideoPlayAuth`）+ **Aliplayer**，**不再是**「HLS 标准加密 + 自建 `authToken`/`keyToken` + `playUrl`」。原第 29 号解密密钥接口已删除（§8.2 墓碑小节）。
>
> **闸口只剩这一个了。** 私有加密把密钥分发交给点播服务，越权面没有消失、只是换了守门人 —— **本接口从「拦得住能不能拿到地址」变成了唯一的那道闸**，下面的校验链因此**一条都不能少**。

- **方法+路径**：`POST /api/v1/vod/play-auth`
- **权限**：`student`（本人播放）；`org_admin` / `teacher` 管理端预览时同样调用本接口（跳过第 2 步的学生授权校验，改按 0.2 资源可见性校验该课程自有或被授权；预览产生的心跳不计入任何学生进度，服务端按 user_type 直接丢弃）
- **服务端校验链（按序执行，任一失败即终止）—— 五步一条不能少，与加密方式无关**：
  1. **学生在读**：学籍状态有效（`org_student.status=0`）。**这是撤销之外唯一的失效手段**（F-103：授权一律永久有效，没有到期日）；
  2. 课时校验：`lessonId` 对应课时存在、未删除、`status=1` 可见、`lesson_type=1` 视频，否则返回 20014；
  3. **授权校验（学生）**：**该学生节点被授权该课程**——`org_resource_grant` 存在 `resource_type=1 AND resource_id=课程ID AND target_node_id=本学生节点ID AND deleted_at=0`；**判定不回溯祖先链**（授权给其导师/管理员节点不算数），不满足返回 20013；
  4. 课程已上架：课程 `status=1`，否则 20013；
  5. 视频校验：关联 `vod_video` 存在且 `status=2` 正常——`status∈{0,1}` 返回 20003（转码未完成），`status∈{3,9}` 返回 20015。

> **这五步是原文，一条都没动。** 换加密方式动的是「拿到什么东西去播」，不是「谁有资格播」。**若将来有人为了让播放更顺畅而简化其中任何一步，请先读上面那句「闸口只剩这一个了」。**

- **响应内容与生成规则**：

| 字段 | 生成规则 |
| --- | --- |
| vid | 阿里云点播的媒资 ID（`vod_video.vod_file_id`）。Aliplayer 以 `vid + playauth` 起播 |
| playAuth | 调用阿里云 `GetVideoPlayAuth` 取得的播放凭证串。**由点播服务签发、有自己的有效期**，不是我们自造的令牌。POC 实测长度 2288（`poc/r1a-aliplayer/RESULT.md` 四项判定表 ②） |
| encryptType | **按 `vod_video.encrypt_type` 逐行翻译**（F-114 改，原文是「固定 `1`」）：库里 `2` 私有加密 → 下发 **1**；`0` 不加密 / `1` HLS 标准加密 → 下发 **0**。<br>**⚠ 它与 `vod_video.encrypt_type` 不是同一套编号，不要互相赋值** —— 两边都叫 encryptType、都是小整数、都在描述同一件事（F-112 已点名这是必然会有人踩的地方）。Aliplayer 的这个参数**只表示「是不是私有加密」**，不是「加没加密」，所以标准加密也下发 0（它由播放器按 m3u8 里的 `#EXT-X-KEY` 自己处理）。<br>**为什么必须做成映射而不是换一个固定值**：F-114 定案第一版不加密（新媒资 `encrypt_type=0`），而**存量视频是 `2`，两者会长期混在一起**。写死任何一个值都会让另一半播不了 —— 明文流被当成私有加密去解密、或反过来 —— 而那个表现是「视频打不开」，**与代码 bug 不可区分**。 |
| sessionId | 32 位随机播放会话 ID（UUID 去横线），标识**本次播放**而非本次取证。心跳请求体携带，服务端据此做同课时会话择一（见 8.3.1 规则 9）。**换发 `playAuth` 时 `sessionId` 保持不变**——换的是凭证，播放会话没断 |
| authToken | 32 位随机凭证（UUID 去横线），绑定 studentId + lessonId，Redis 存储，TTL 300s；心跳请求头 `X-Play-Token` 携带。**它只用于心跳，与解密无关**——解密由 Aliplayer 拿 `playAuth` 向点播服务完成，我们既不发密钥也看不到密钥 |
| authExpire | `authToken` 有效秒数，固定 300 |
| maxPosition | 本人历史最远触达位置（秒）= `vod_watch_progress.max_position` 与 Redis 缓冲取较大值；仅随正常播放推进。<br>**⚠ F-113 后它的用途变了**：~~「允许拖拽上限」「`watchStatus=2` 后同样限制拖拽、不解除禁快进」~~ **已失效**——拖拽完全放开，且第一版不会出现 `watchStatus=2`（完播判定延后）。<br>**现在的用途**：它是**第一版唯一能反映「看到多深」的数据**，与 `watchedDuration` 配合识别"反复看开头"（时长 60 分钟 + `maxPosition` 10 分钟 = 一直在看开头）。对齐 PRD F2-5 规则 2 与 02-数据库设计 §4.2.7 |
| ~~watermark.text~~<br>~~watermark.interval~~ | **【F-114：第一版不下发】** 需方 2026-08-21 定案<b>水印第一版不做</b>，本接口<b>不返回 watermark 字段</b>。<br>原文保留供将来启用时照抄：水印文本 = 学生「真实姓名 + 手机号」（录屏溯源，例 `李子墨 13812345678`），取自 `sys_user.real_name` / `sys_user.phone`；**学生端（`viewer_type=3`）一律中间四位打星、不读租户配置、不可关闭**（受《个人信息保护法》第 31 条约束的是未成年人信息，「允许租户选择不脱敏」本身不成立，契约 §7.2 第 2 条）；管理端预览（`viewer_type ∈ {1,2}`）读 `watermark_phone_mask`（默认 1 脱敏）；`interval` 为 8~15 秒随机下发、前端据此把水印移到画面随机位置。<br>**⚠ 将来启用前先读 `poc/r1a-aliplayer/RESULT.md`**：2026-08-21 实测 **iOS 微信全屏下 DOM 水印不成立**（`webkitbeginfullscreen` 由系统播放器接管），且**水印自检在那期间会报假绿**。 |
| watchedDuration / watchStatus | 本人当前进度快照（合并 Redis），供播放器续播定位与 UI 展示 |

> **原 `playUrl` 字段已删除。** 它当初是「加密 m3u8 地址 + `?auth_key=...`（URL 鉴权防盗链）+ `&MtsHlsUriToken=...`（把身份透传给密钥接口）」。私有加密下播放器拿 `vid + playAuth` 起播、地址由 SDK 自己取，**这三样东西一样都不需要**。「控制台开启 HLS 标准加密参数透传」那一步同样删除 —— 那是标准加密专有的开关。
>
> **`ALIYUN_KMS_*` 两项本期不消费**（契约 §1 订正段已写明）：密钥由点播服务托管，我们不取密钥、也不下发密钥。

- **审计**：每次成功发放，同步写 `vod_play_auth_log`（`viewer_user_id` = 当前账号、`viewer_type` = 其 `user_type`、`lesson_id`、`video_id`、`auth_token`、`expire_time`、`client_ip`）。**`student_id` 仅 `viewer_type=3` 时写入**，管理端预览留 NULL——教师与管理员没有 `org_student` 档案行。管理端预览**同样必须落审计**：能看到全机构课程的人批量取证，正是最需要留痕的场景。**`event_type` 恒为 1**（播放凭证）——取值 2（解密密钥）随接口 29 删除而不再被写入，见 §8.2。

#### 8.1.1 换发凭证与「撤销何时生效」（F-106 定案，**本节明知地推翻两处权威文档**）

**两种凭证、两个有效期，不要混：**

| | 谁签发 | 用途 | 过期表现 |
| --- | --- | --- | --- |
| `authToken` | 我们 | 心跳的身份 | 心跳返回 **20001**，播放器无感重调 8.1 |
| `playAuth` | 阿里云点播服务 | 解密与播放 | 播放器侧报凭证过期，需要重新取 |

**〔F-106 定案〕撤销从「下一次点开视频」起生效。正在播放的那个视频可以看完。**

- **心跳【不重判授权】**：8.3.1 规则 1 只校验 `X-Play-Token` 本身，**不回库重跑 `org_resource_grant`**；
- **换发 `authToken` / `playAuth` 时【也不重判】**：换发就是换一张同样的票，不是一次新的准入。

**需方的理由**（原话口径）：公司内部学生使用，最坏是多看半节课的后半段，不值得为它在**每 10 秒一次的心跳**上加一次授权查询。

> **⚠ 这一条明知地推翻了下面两处，逐条列出，不是遗漏：**
>
> - **`PRD FR-4 规则 4`** 逐字「对正在学习的学员**即时生效**」——原文是「撤销后，正在播放的学员在下一次心跳或播放凭证续签时被拒（20013 / 20001）」。**规则 4 的后半句（学习记录不清零）不受影响。**
> - **`DESIGN-CONTRACT §1`** 把「**撤销后播放中断，不是等凭证过期**」列为核心验收场景。§1 那段论证（不做密钥侧校验的话「凭证过期、授权被撤销都拦不住他继续解密播放」）**本身仍然成立** —— 它说的是「连**下一次**都拦不住」，而需方接受的是「**到下一次为止**」这个窗口。**两者不是同一件事，不要拿它当推翻的依据。**
>
> **窗口有多大**：一个视频的剩余时长。**不是无限** —— 他看的仍是同一个视频，看完就完了；下一次点开任何视频都会走完整的五步校验链。

- **【只登记，不加限制】`playAuth` 有自己的有效期，播放中过期要换新的。** 按本节「换发不重判」，**一个学生只要不关页面，理论上可以一直换下去**。这是上面那条定案的直接推论，写在这里是为了让它**被看见**，**不是一个待办**：他看的仍然是同一个视频，看完就完了。**需方没有提过要限制换发次数或总时长，实现方不自加**——若将来要限，那是一次新的需方定案，不是实现细节。

- **给模块 13 的提示（零成本，不在本轮实施）**：即便不在心跳里查库，也有**推**的做法 —— **撤销时主动删掉受影响学生的 `play:auth` Redis 键**。心跳本来就要读那些键（模块 13 心跳规则 1），键没了就自动被拒，**一次额外查询都不用加**。需方选的口径不要求这么快，但这条路存在。

| sessionId | string | 否 | **换发时回传**原会话 ID，服务端原样返回、播放会话不中断；首次取证留空，由服务端生成 |

### 8.2 ~~获取解密密钥~~（接口 29，**已删除**）

> **加密路线由「HLS 标准加密 + 自建密钥接口」改为「阿里云私有加密 + VidAuth」，本接口随之删除。** 接口总数 160 → 159；03-03 分册 34 → 33（模块 12 由 2 个接口变 1 个）。
>
> **为什么是删除而不是改写**：私有加密下**解密由播放器 SDK（Aliplayer）拿 `VidAuth` 自己完成，密钥由点播服务托管** —— POC 实测记录（`poc/r1a-aliplayer/RESULT.md` 验证对象表）逐字：「密钥分发：点播服务托管，**无自建密钥接口**」。也就是说，**「学生端向我们取密钥」这个动作在新路线下压根不存在**，不是换个路径或换个参数的事。
>
> **小节编号保留为墓碑**：§8.3 / §8.4 / §8.5 不上移，理由与 03-02 §9.4 那条墓碑小节逐字相同 —— 全库有大量「§8.x」交叉引用，重编号收益为零，而**指错了不会有任何症状**。目录里 **29 号从此空缺**，`scripts/check_consistency.py` 的 `_RETIRED_INTERFACES` 登记了退役理由；**未登记的缺口照常 ERROR**。
>
> **它当初为什么必须独立存在**（留着，因为它记录的是一个**真问题**，而不只是一个接口）：标准加密下 m3u8 与 TS 分片由 CDN 直出，`auth_key` 只防盗链、不防越权 —— 学生只要拿到 m3u8 地址，**凭证过期、授权被撤销都拦不住他继续解密播放**，因为他不再需要回来续签任何东西。那条论证是对的，它要求"取密钥"这个动作必须回到服务端、且必须重跑完整授权判定。
>
> **换成私有加密之后，这个越权面并没有消失，只是换了守门人**：解密密钥改由阿里云点播服务按 `VidAuth` 分发，**闸口从「我们的密钥接口」前移到「我们签发 `VidAuth`」这一步**。所以 §8.1 的校验链**一条都不能少** —— 它从"拦得住能不能拿到地址"变成了**唯一**的那道闸。详见 §8.1 与 04 §B 模块 12。
>
> **随之一并失去适用对象的三条**（都曾是本节的承重规则，写在这里以免将来有人当成"漏掉了"）：<br>① `keyToken` 的 TTL 必须 ≤ `authExpire` —— 没有 `keyToken` 了；<br>② `MtsHlsUriToken` 身份通道与「控制台开启 HLS 标准加密参数透传」—— 私有加密不经过这条路；<br>③ `vod_play_auth_log.event_type=2`（解密密钥）—— **该取值从此不会被写入**，`event_type=1`（播放凭证）成为唯一取值。**DDL 与枚举不动**：留着比改掉便宜，且它记录着这条路线存在过。
>

### 8.3 播放心跳上报

- **方法+路径**：`POST /api/v1/vod/heartbeat`
- **权限**：`student`（仅累计本人进度）
- **签名**：本接口为全系统最高频接口，请求体与响应体签名与契约 6.4 **完全一致**，任何字段不得增删改名。**F-113 明知推翻过一次**：新增 `sessionPlayedSeconds`（观看时长改由前端计算）。C15 核契约 §6.4 / PRD F2-7 / 本表三处。
- **上报频率**：播放器每 10s 上报一次（原始需求）；暂停时停止上报，恢复播放后继续。
- **请求头**：除 `Authorization` 外，须携带 `X-Play-Token: {authToken}`（8.1 发放，300s 有效）。

**请求参数（Body，契约 6.4 固定签名）**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| lessonId | string | 是 | 课时 ID |
| videoId | string | 是 | 媒资 ID（`vod_video.id`），须与课时当前关联一致 |
| currentTime | number | 是 | 当前播放位置（秒，允许一位小数） |
| duration | number | 是 | 播放器读取的视频总时长（秒） |
| playRate | number | 是 | 当前倍速（0.5~3.0） |
| seeked | boolean | 是 | **本次心跳前是否发生过 seek 或暂停恢复**：用户拖动进度条后、或从暂停恢复播放后的**第一次**心跳置 `true`，其余一律 `false`。`true` 时服务端重置规则 6 的推进校验基准（本次不做推进判定）。**规则 3 已废止（F-113），原文那句"规则 3 的拖拽上限仍照常生效"一并删除。** 缺省不得省略——服务端把缺失视为 `false`，会让拖动后的心跳被判为异常并污染日志 |
| sessionId | string | 是 | **本次播放会话 ID**，取自 8.1 响应（续签不变）。服务端按 `{studentId}:{lessonId}` 维护当前活跃会话：同会话正常计时；不同会话且当前会话 60s 内仍活跃时返回 **20020**，本次不计时长（见 8.3.1 规则 9） |
| sessionPlayedSeconds | integer | 是 | **本会话累计真播秒数（F-113 新增）**，由**前端计时器**给出。服务端 `delta = max(0, 本次值 − 该会话上次值)`，再 `delta = min(delta, Δt + 5)` 做物理上限截断，然后 `watched_duration += delta`。<br>**三条实现约束**：① **累计的是墙钟不是媒体时间**——`playRate` 不参与计时，监听 `timeupdate` 累加 `currentTime` 增量的写法会让 2 倍速播 5 分钟算成 10 分钟，**正好推翻规则 4**；② **报累计不报增量**——重发时 `delta=0` 天然幂等、丢包时下次自动补回；③ 页面刷新＝新会话，累计从 0 重起，**规则 9 接管时基准置 0** |
| trigger | string | 是 | **本条心跳的触发原因（F-116 新增，第 9 个字段）**，取值 `tick` / `pause` / `resume` / `ended` / `leave`。<br>`tick` = 播放中每 10 秒的**周期心跳**；其余四种为**事件心跳**（暂停 / 恢复 / 播完 / 离开页面）。<br>**服务端据此分流规则 2**：`tick` 走 8 秒间隔校验；**其余一律采纳，不做任何间隔限制**。<br>**为什么必须是新字段而不是从别处推**：8 个老字段里没有任何信息说明心跳类型 —— `seeked` 只在"拖动后/恢复后第一条"为 `true`，盖不住暂停、盖不住离开页面，语义也是另一件事。<br>**为什么用枚举不用布尔**：它会落进 `vod_heartbeat_log`，**顺带说明每条心跳是为什么来的**；布尔只能答"是不是周期的"，枚举能答"学生当时在干什么"。<br>缺失或取值非法 → 按规则 5 丢弃（不得默认成 `tick`：那会让事件心跳被当成周期心跳去卡 8 秒闸）|

**请求示例**

```json
{
  "lessonId": "1954103000000000002",
  "videoId": "1954200000000000002",
  "currentTime": 123.4,
  "duration": 600,
  "playRate": 1.0,
  "seeked": false,
  "sessionId": "3d5b81c04e7a4a92b6f0c8e2d1a97b53",
  "sessionPlayedSeconds": 118
}
```

#### 8.3.1 服务端校验规则（编号权威定义；F-113 后规则 3 为墓碑）

> **⚠ F-113 前提：不防刷课**（需方 2026-08-21 定案，原话「刷课不需要防」）。本节原标题为「九条校验规则（**防刷核心**）」——
> **保留下来的规则大多换了理由**：留痕、诊断、兜 bug。**理由必须写实**，一条理由已经不成立的规则留在文档里，
> 下一个人会照着那个假理由做决定（F-100、F-111 各栽过一次）。
>
> **⚠ 观看时长由前端计时器给出，服务端不再自己计时**（F-113 定案二）。因此**任何规则都不得以"本次不计时长"作为处置**——
> 后端一旦这么做，就等于又在自己算时长，那就变回**两个数字表示同一件事**。规则 6 为此降级为只留痕。

| # | 规则 | 判定与处理 |
| --- | --- | --- |
| 1 | **凭证有效** | `X-Play-Token` 必须存在、未过期（TTL 300s）、且 Redis 中绑定的 studentId/lessonId 与本次请求一致；不通过返回 **20001**，客户端无感调 8.1 续签后重试本次心跳 |
| 2 | **间隔校验**（限流；F-116 按 `trigger` 分流） | **① `trigger = tick`（周期心跳）**：取与上一次**有效**心跳的服务端接收时间差 Δt（首次心跳以凭证发放时间为锚点）。Δt ≥ 8s 有效；**Δt < 8s 判为异常，走规则 5**（丢弃 + `20002`，`reject_rule=2`）。<br>**② `trigger ≠ tick`（事件心跳：`pause` / `resume` / `ended` / `leave`）**：**一律采纳，不做任何间隔限制。**<br>**③ 异常心跳的日志限流**（保护 `vod_heartbeat_log`）：每会话每分钟最多写 **20** 条异常明细；第 21 条时写**一条汇总行**（`reject_rule=2`，备注"本分钟异常已达 20 条，后续静默丢弃"），此后**仍然拒绝并返回 `20002`，但不再写明细**。**精确条数不靠日志表，靠指标** `heartbeat_reject_total{rule}`（契约 §7.1）—— 那本来就是计数用的，而日志表是留证据用的，两者分工不同。<br><br>**⚠ 为什么按 `trigger` 分流（F-116，需方 2026-08-22 定案）**：F-113 之后前端除周期心跳外，还会在**停下来 / 恢复 / 播完 / 离开页面**四类时刻各发一条**事件心跳**（需方「暂停期间不允许心跳」那条要求的直接产物）。**事件心跳本来就不看表**，硬 8 秒闸会把它们大量判为异常：**真机实测 23 条心跳被丢 12 条（52%），前端算 76.3 秒而服务端只入库 69.3 秒，差的 7.0 秒丢在【最后一条暂停心跳】上，它之后没有任何心跳来补**。<br>**事件心跳不设任何上限**：它的条数由**用户操作频率**天然限死（暂停几次就几条），不是刷时长的载体；而闸 ② 已经给了每条 delta 的物理上限。**限流的对象是周期心跳与高频空包，不是事件心跳。**<br>**规则 2 剩下的唯一理由就是限流**（保护 Redis 与日志表）——「防重复投递」那一半已随「报累计不报增量」失效，「防刷课」需方早已定案不做。<br>**⚠ `trigger` 缺失或取值非法一律按规则 5 丢弃，不得默认成 `tick`** —— 默认成 `tick` 会让事件心跳重新被卡在 8 秒闸上，等于这条定案没做。 |
| 3 | **【已废止 · 墓碑（F-113）】拖拽校验** | 原文：「`currentTime` 不得超过 `maxPosition + 15`；超出视为绕过前端「禁用快进」的非法拖拽或报文篡改，走规则 5。」<br>**禁快进取消后本条失去对象。****编号 3 从此不写入 `reject_rule`、不得复用，4~9 号不上移**——编号已随该列持久化进按月分区的审计表，重编号收益为零而指错了没有任何症状（照 §8.2 接口 29 的墓碑先例）。<br>**`maxPosition = max(maxPosition, currentTime)` 的更新动作没有随本条废止**，移入 §8.3.2 处理流程；`maxPosition` 换了用途，见该节 |
| 4 | **倍速不加速累计** | `playRate > 1` 时**不加速累计**：`watchedDuration` 增量只按规则 2 的服务端墙钟间隔计算，与 playRate 无关——2 倍速看 10s 仍只计 10s（防倍速刷完播）；playRate 仅落 `vod_heartbeat_log` 供行为分析 |
| 5 | **异常心跳丢弃**（F-113 收窄） | 凡未通过规则 **2**，或参数明显非法（`currentTime<0`、`currentTime>duration+2`（合法区间 [0, duration+2]，对齐 PRD F2-7 **校验规则 5**）、`duration` 与媒资 `vod_video.duration` 偏差 >5%、`playRate` 超出 0.5~3.0、**`sessionPlayedSeconds` 为负 / 非整数 / 缺失**），一律**丢弃**，明细仍写 `vod_heartbeat_log` 备查（interval_sec 记实际值），返回 **code=20002**。<br>**删去「未通过规则 3」**（已废止）。<br>**⚠ 明确禁止：不得因规则 6 的判定结果去扣时长。** 本条只处理**参数非法** |

| 6 | **推进一致性**（挂机/空跑**留痕**；F-113 降级） | **判定逻辑不变**：仅在连续两次 `seeked = false` 的心跳之间校验，`Δ currentTime` 须落在 `[0.5, 1.5] × Δt × playRate` 区间；长期零推进（连续 5 次 `Δ currentTime ≈ 0` 而 `Δt` 正常、期间无 `seeked = true`）判定为挂机或纯脚本上报。<br>**⚠ 处置变了，这是本轮最容易实现错的一条**：<br>　原：检测到异常 → 本次**不计入 `watchedDuration`**（**后端在算时长**）<br>　新：检测到异常 → **只写 `vod_heartbeat_log` 留痕**（`reject_rule = 6`），**不影响时长、不丢弃心跳**<br>**为什么必须这样**：时长既然由前端给，后端一旦说「这条我不给你算」，**后端就等于又在自己算时长**，那就变回**两个数字表示同一件事**——本项目反复吃亏的形态。<br>**`seeked` 自身的滥用防护**：连续 `seeked = true` 不得超过 **2 次**（不变），单学生单课时每小时不超过 **180 次**（**F-113 由 20 提高**）；超出按规则 5 丢弃并计入 `reject_rule`。<br>**20 → 180 的理由**：20 是在**禁快进**前提下定的——那时学生只能在已看范围内小幅回拖。**放开拖动后一小时拖 20 次是完全正常的观看行为**，再按旧值卡会把**被明确允许的行为持续判为异常**，而学生只看到时长莫名其妙少了、前端毫无提示——与规则 9 那个「永久归零」同类失效。180 ≈ 平均每 30 秒可拖一次，仍挡得住"每 10 秒 seek 一次"的脚本模式。<br>**⚠ 这个上限保护的对象也变了，理由要写实**：时长已经不由本条决定，所以它**保护不了时长的准确性**；它保护的是**日志的诊断价值**——脚本若恒置 `true`，本条永不判定，`vod_heartbeat_log` 就再也看不出这个学生有没有在真的播放，而**日志是第一版唯一的行为事实来源**。<br>**原文那段「不设本条时脚本可 1:1 刷满时长、刷课收益率由规则 4 与规则 8 兜住」已删除**：前提（防刷课）已取消 |
| 7 | **并发课时数上限** | 单学生**同一时刻活跃课时数 ≤ 2**（活跃 = 60s 内有有效心跳）。超出的课时心跳直接丢弃，并计入 `vod_heartbeat_log.reject_rule`，由风控报表按 `(student_id, lesson_id, 时间窗)` 聚合呈现。<br>原有的并发防护只作用在"同一课时"（Redis key 含 lessonId），**跨课时并行完全不受限**——20 个课时并行的脚本一晚可刷完整门课程，这是防刷模型此前最大的缺口 |
| 8 | **时长封顶**（F-113 理由改写：兜 bug，不是防刷） | 单学生**单日** `watchedDuration` 累计上限 10 小时、**单课时**累计上限 `duration × 3`。超出部分只记录不计入，并计入 `vod_heartbeat_log.reject_rule`，由报表按 `(student_id, lesson_id, 时间窗)` 聚合呈现供机构核查。<br>**⚠ 理由由「防刷」改为「兜前端计时器 bug」**：前提已取消（不防刷课）。本条现在防的是——浏览器冻结后台标签页定时器，页面醒来时写得糙的计时器一口气报出几小时。**那不是作弊，是 bug**，而它会污染报表。**不设风控分列**——该名词若建成字段就要定义算法、衰减、阈值与清零时机，四项全无定义；本表已是完备的原始事实 |
| 9 | **同课时会话择一**（多端并发） | Redis 按 `vod:hb:{studentId}:{lessonId}` 维护 `activeSessionId` 与其最后心跳时间。心跳的 `sessionId` **与之相同**：正常处理；**不同**且当前活跃会话在 **60s** 内有过有效心跳：返回 **20020**，本次不计时长、不推进任何基准，明细仍写 `vod_heartbeat_log`；**不同**且当前活跃会话已超 60s 无心跳（关页面、断网、切设备）：**新会话接管**，改写 `activeSessionId`，并**同时重置规则 6 的推进基准与 `sessionPlayedSeconds` 的累计值基准（置 0）**。<br>**累计值基准必须一并重置**（F-113）：不重置的话，新设备第一条心跳的累计值小于上一端，`delta = max(0, …)` 恒为 0，**时长永远不涨**。<br><br>**⚠ F-113 之后本条的理由整段换了，旧论证不再成立。**<br>**旧论证（保留供回溯，已失效）**：不做会话择一的真实后果是**永久归零**——两端交替时另一端的心跳会被**规则 6 判为位置跳变而拒绝**，被拒的心跳不推进基准，就此锁死，学生此后一小时时长累计约等于 0。<br>**为什么失效**：**规则 6 已降级为只留痕、不再拒绝任何心跳**，那条锁死链路的**第一环就断了**。**照抄旧理由会推出「`sessionId` 可以不要」的错误结论。**<br>**新理由，两件事都还成立**：**①** `sessionPlayedSeconds` 是**按会话**累计的，服务端必须知道累计值属于哪一次播放才能算出 `delta`——没有会话作用域，两端的累计值互相顶，`delta` 时正时负；**②** 两端同时播放、各自计时器都在走，若都被采纳，**同一段真实时间会被计两次**。旧论证是"算不出来"，新论证是"**算多了**" |

> 规则 6~9 的阈值（`[0.5,1.5]` 区间、连续 seeked 上限 2 次、**每小时 seeked 上限 180 次（F-113 由 20 提高）**、活跃课时数 2、单日 10h、单课时 3 倍、会话接管静默期 60s）为平台级默认值，不属于租户配置键；调整需修订本文档与 PRD F2-7。**本次即为该修订。**
>
> **〔已删除〕原有一段「规则 3 与 `seeked` 无关」的注记**：它论证的是「若对 seek 心跳放开规则 3，禁快进就被绕过」。**规则 3 已废止（F-113），论证的对象不存在了**，故整段删除而不是改写。

> **每条心跳都写 `vod_heartbeat_log`，并以 `reject_rule` 记录判定结果**（0 采纳，**2/5/6/7/8/9** = 被本表对应编号的规则命中；**`3` 自 F-113 起不再写入，见墓碑行**。**注意 `6` 现在表示「留痕」而非「拒绝」**——规则 6 已降级，命中它的心跳仍被采纳、时长照算）。没有这一列时，只有规则 2 的拒绝能从 `interval_sec < 8` 反推，其余完全不可追溯——而"学生说学了一小时、系统只记了十分钟"正是最需要逐条回放的场景。
>
> **本表的规则编号是 `reject_rule` 的取值域，也是 PRD F2-7 校验规则列表的编号来源，三处必须一致**——编号已随该列持久化进审计表，改号会让数年的历史日志指向另一条规则且无法回溯修正。
>
> **`1`、`3`、`4` 保留不使用**：规则 1 在进入心跳处理前即被拦下（返回 20001），此时尚未通过学生↔课时绑定校验，不应写归属到某学生的审计行；**规则 3 已废止（F-113），编号留墓碑、不复用**；规则 4 是计时口径、不拒绝心跳，`playRate` 越界由规则 5 承担。
>
> **规则 2 失败虽由规则 5 统一返回 `20002`，`reject_rule` 记的是首次判定失败的那条（`2`）**，`5` 专指参数明显非法；若一律记 5，该列就退化为"要么 0 要么 5"，丧失诊断价值。（原文含规则 3，随其废止删去。）
>
> **被拒绝的心跳一律不推进任何基准**（规则 2 的时间基准、规则 6 的位置基准、`maxPosition`、`last_position`、**`sessionPlayedSeconds` 的累计值基准**）。唯一的例外是规则 9 的会话接管：接管时**必须**同时重置位置基准**与累计值基准（置 0）**，否则新设备第一条心跳会因位置跳变被记异常、且 `delta` 恒为 0 导致时长永不增长，接管等于没发生。

**异常心跳响应示例**

```json
{
  "code": 20002,
  "msg": "心跳间隔异常，本次已丢弃",
  "data": null
}
```

#### 8.3.2 Redis 缓冲 + 批量落盘（对齐契约 6.4 与原始需求第四节）

1. 有效心跳**只写 Redis，不直接写库**：`key = vod:hb:{studentId}:{lessonId}`（Hash：watchedDuration / maxPosition / **lastPosition** / watchStatus / lastHeartbeatTime / videoId / courseId / **activeSessionId** / **sessionPlayedBase**，TTL 24h），并将 key 加入脏集合 `vod:hb:dirty`。
   > **`sessionPlayedBase`（F-113 新增）**：该会话上一次上报的 `sessionPlayedSeconds`，用于算 `delta`。**规则 9 会话接管时置 0。**

1.1. **时长累加与上界截断（F-113）**：

   ```
   delta = max(0, 本次 sessionPlayedSeconds − sessionPlayedBase)
   delta = min(delta, Δt + 5)        // 物理上限截断，Δt = 服务端接收时间差
   watchedDuration += delta ；sessionPlayedBase = 本次 sessionPlayedSeconds
   ```

   **`min(delta, Δt + 5)` 是上界，不是第二个真相。** 它兜的是前端 bug——浏览器冻结后台标签页定时器，页面醒来时写得糙的计时器可能一口气报出几小时。**服务端不重算时长，只拒绝物理上不可能的增量**；**一个数、一个封顶，不构成两个数字打架**，不要把它"补全"成第二套计时。截断发生时写 `vod_heartbeat_log` 留痕，**不占用 `reject_rule`**（心跳被采纳了，只是增量被削）。

1.2. **位置字段推进**：`maxPosition = max(maxPosition, currentTime)`；`lastPosition = currentTime`（直写，不取大，供 8.4 断点续播）。**原由规则 3 承担的 `maxPosition` 更新动作移到这里**——规则 3 已废止（F-113），但更新动作本身没有随之消失。
2. **XXL-Job 每 60s** 扫描脏集合，批量 UPSERT `vod_watch_progress`（UK student_id + lesson_id），心跳明细批量插入 `vod_heartbeat_log`（按月分区，允许归档清理）；落盘成功后移出脏集合。极端情况下（实例宕机）最多丢失 60s 内的增量，可接受。
3. **【第一版不执行】完播判定**（F-113 定案四）：`watch_status` 只在 0/1 之间流转、**不写 2**，`complete_time` 恒空。
   > **需方原话**：「我们不会重算的，如果后续要，也只会要每个学生在那堂课上花了多少时间」——那个数就是 `vod_watch_progress.watched_duration`，**第一版从模块 13 上线那天起就在存**，不需要额外工作。
   > **将来启用时的逻辑原样保留**：在第 2 步 XXL-Job 落盘时逐条比较 `watchedDuration ≥ duration × complete_rate_threshold`（租户级配置，默认 90%，契约第 5 节）→ 回填 `watch_status = 2`、记 `complete_time`，并同步刷新 Redis 缓冲中的 `watchStatus`；状态单向流转（0→1→2），不回退。**启用后只对此后的落盘生效，本项目不做历史回算。**
   > 原文末句「`maxPosition` 始终只由规则 3 推进，**完播后不解除拖拽限制**」**已失效**：规则 3 已废止、拖拽本就不受限，推进动作移至 1.2。
4. 所有进度查询接口（6.1、6.2、8.3、8.4）读取时合并 Redis 缓冲与 DB，取较大值，保证准实时。

#### 8.3.3 客户端降级策略

- 收到 **20002**：**静默降级**——不弹窗、不打断播放、不回退进度条，丢弃本次结果，按原 10s 周期继续上报；连续 3 次及以上 20002 时前端仅上报监控埋点。
- 收到 **20001**：无感调用 8.1 换发凭证后继续上报，播放不中断。

> **⚠ 规则 1 只校验 `X-Play-Token` 本身，【不回库重跑授权判定】—— 这是 F-106 的定案，不是漏写。**
> 需方 2026-08-21 定案「撤销从**下一次点开视频**起生效，正在播放的那个可以看完」，理由是不值得为它在**每 10 秒一次**的心跳上加一次授权查询（口径与窗口大小见 §8.1.1）。
>
> **这一条推翻了 `PRD FR-4 规则 4` 的「即时生效」与 `DESIGN-CONTRACT §1` 的核心验收场景**，两处都已在原处标注。**下一个人若在这里加一次 `org_resource_grant` 查询，改的是需方定案，不是补一个 bug。**
>
> **真要更快也不必查库**（模块 13 的提示）：撤销时主动删掉受影响学生的 `play:auth` 键 —— 规则 1 本来就要读那些键，键没了自动被拒，**一次额外查询都不用加**。
- 收到 **20020**：**暂停播放并明确提示**「该课时正在其他设备播放，请先关闭其他设备」，提供「在本设备继续」按钮——点击后前端停止上报 60s，待原会话静默期满自动接管（不提供强制抢占接口，避免变成互相抢占的死循环）。**本码不得静默降级**：它与 20002 的性质完全不同，20002 是"这一条不算"，20020 是"你这一端的时长全都不算"，静默处理等于让用户白学一小时。
- 网络失败：本次心跳直接丢弃，不做本地补偿重发（防止补发报文被规则 2 判异常），下个周期正常上报。

**相关业务错误码**：20001、20002、20014（课时被删除或隐藏后仍在上报）、20020（同课时已在其他设备播放）。

## 附：本模块状态机速查

**课程 `crs_course.status`**：0 草稿 →（上架）→ 1 已上架 ↔（下架/再上架）↔ 2 已下架；仅 0/2 可删除。

**媒资 `vod_video.status`**：0 上传中 →（`FileUploadComplete` 事件）→ 1 转码中 →（`TranscodeComplete(success)` 事件）→ 2 正常 / （`TranscodeComplete(fail)` 事件）→ 3 转码失败；3 →（接口 33 重新发起转码 / 接口 25 获取视频上传凭证 重传源文件）→ 1；2 ↔ 9 禁用/启用经接口 34 媒资禁用/启用 人工操作；仅 2 可挂课时、可发放播放凭证。**事件经 XXL-Job 拉取轻量消息队列消费，不是 HTTP 回调**（§7.2）。

**完播 `vod_watch_progress.watch_status`**：视频课时 0 未开始 →（首个有效心跳）→ 1 学习中 →（落盘时判定 watched_duration ≥ duration × 90%，阈值租户可配 `complete_rate_threshold`）→ 2 已完成；**图文课时首次成功访问直接 0 → 2（不经过 1，见 §6.3）**。单向流转不回退。
