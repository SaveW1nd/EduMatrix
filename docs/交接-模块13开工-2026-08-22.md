## 这个项目的工作纪律（不遵守会被打回）

**关于判断**
- **需方拍板的事一律先问我**，别自己定；问的时候用大白话，别用术语
- 我给的方案/说法**可能是错的**，你查证后如果不成立，**直接说不成立并给证据**，不要顺着做
- 我说的数字（阈值、上限）**要用实测核**，核不动就说核不动

**关于证据**
- **不许凭印象报结论**。说"改好了"要贴实测输出；说"检查通过"要贴那一行
- **脚本打印「已改」不是文件被改了的证据**，提交信息更不是。提交前后都要核 `git show :file` / `git show HEAD:file` 的**实际内容**——这一条是吃过亏才立的（有一次提交信息声称改了某文件，实际一个字都没进去）
- 数字**现跑现写**，不许沿用上一轮的

**关于测试**
- 每条用例要对应**一次真实发生过的故障或一条契约铁律**，不许为凑数写
- 每个守卫都要有**变异**证明它承重。**拆掉它没有用例变红 = 那个守卫没人守**
- 变异点名用例时**必须逐字引用用例名**，不许写「XX 相关」——写不出具体名字，通常说明那条用例不存在
- 交付前自查两问：**哪几行一次都没执行到**、**哪两个分支我其实区分不了**

**关于文档**
- 契约 / PRD / API 分册是**权威源**，实施方案与它们冲突时以它们为准
- 规则改了理由要**写实**。留着一条理由已经不成立的规则，比删掉它更危险
- 废止的规则**留墓碑、编号不复用**（`reject_rule` 已随审计表持久化，改号会让历史日志指向另一条规则）

**关于提交**
- commit 后**直接 push，不用问**；建 PR 与 merge 要我明确要求
- `backend/` 改动要单独说明；文档改动要写清落地位置
