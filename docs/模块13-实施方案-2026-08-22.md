## 2. 职责边界（一句话铁律）

> **观看时长由前端算，服务端不算。服务端只做三件事：接收、限界、持久化。**
>
> **服务端任何地方重新计算时长即为缺陷。** 出现第二个时长来源，两份迟早分叉，
> 而分叉的表现是"两个页面显示的时长不一样"——不报错。

```
前端                              服务端（模块 13）
─────────────────────────        ────────────────────────────────
按墙钟累计"真播秒数"        ──→   收下 → 三道闸 → Redis 缓冲 → 60s 批量落盘
按下表的时机上报累计值             读进度供断点续播
```

## 3. 心跳触发时机（上一份缺的就是这张表）

**前端在下列时刻上报，每次都报【当前累计值】而不是增量。**

| # | 触发 | 类型 | 为什么必须有 |
| --- | --- | --- | --- |
| 1 | 正在播放时每 **10 秒** | 周期 | 常规采样 |
| 2 | **停下来那一刻**（`pause` / `waiting` / `seeking` / `ended`） | 事件 | 带走这一段的尾巴；之后进入静默 |
| 3 | **恢复播放那一刻**（`play` / `seeked`） | 事件 | 结束静默，宣告"人回来了" |
| 4 | **离开页面**（`pagehide`，用 `sendBeacon`） | 事件 | **唯一没有下一条来补的心跳** |
| 5 | 停表期间 | **不发** | 需方要求。实测：不做这条时 95 条心跳里 46 条是暂停时白发的 |

**为什么报累计值不报增量**（F-113 定的口径，已被真机救过三次）：
① iOS 实测有 12 条心跳被**重复投递**——报增量会凭空多出 120 秒，报累计值天然幂等；
② 冻结期间丢包不影响正确性，下一条自动补回；
③ 正因如此，停表期间可以放心地不发。

**`ended` 必须发**：它带着最终累计值，而播完之后不会再有任何心跳。

**长时间暂停与凭证 TTL**：`X-Play-Token` TTL 300 秒。学生暂停超过 5 分钟再恢复，
`resume` 心跳会拿到 `20001`。**前端在恢复播放前先续签，不要等心跳被拒再补**——
等被拒再补会让恢复后的第一条心跳丢掉，而那条正好带着暂停前的尾巴。

## 4. 三道闸

### 闸 ① 非负

```
delta = max(0, 本次 sessionPlayedSeconds − 该会话上次值)
```

**拦**：前端算出负值。**历史实例**——POC 计时二版按「视频前进量」计时，往回拖时算出 **−240 秒**。

### 闸 ② 物理上限

```
Δt    = 本次与【上一次被采纳心跳】的服务端接收时间差
delta = min(delta, Δt + 5)
```

**拦**：数量级错误与伪造。上报 500 秒而服务端只过了 10 秒 → 截到 15。

> **⚠ 它不拦锁屏虚增。这句话必须写进代码注释。**
>
> 实测（POC 计时一版，安卓）：
> ```
> 上一条心跳 10:57:57   sessionPlayedSeconds = 61
> 本条心跳   10:59:26   sessionPlayedSeconds = 95.8
> Δt = 89   天花板 = 94   虚增 34.8 < 94   →   原样收下
> ```
> 锁屏期间心跳照发（一版的定时器空转），Δt 随之增大，虚增始终在天花板之下。
>
> **缺这段注释的后果**：后续维护者以为本闸防锁屏，进而删掉前端的计时守卫——
> 而那一层是这类虚增的**唯一防线**。

### 闸 ③ 会话接管时基准置零

会话接管（原活跃会话 60s 无有效心跳）时，**同时**重置：位置基准、**`sessionPlayedSeconds` 累计基准 → 0**。

**拦**：时长永久冻结。不重置时，新设备首条心跳的累计值小于上一端，
`delta = max(0, 负数) = 0` 恒成立，**时长永不增长且不报错**。

## 5. ⚠ 待定案：事件心跳与规则 2 的冲突

规则 2 是「Δt < 8s 判异常 → 走规则 5 → 丢弃 + `20002`」。
而第 3 节的**事件心跳本来就不是按 8 秒来的**。

**真机实测**（把 24 条心跳喂给规则 2）：

```
被丢 12 条 / 共 23 条（52%）
服务端入库 69.3 秒   前端报 76.3 秒   →   差 7.0 秒
丢的 7 秒在【最后一条 stop:pause】上，它之后没有任何心跳来补
```

**损失有界**：Δt 按「上次**被采纳**」算，被丢的心跳不推进基准，
后续心跳的 Δt 自然涨到 ≥8s 必被采纳。**每会话最多丢 8 秒**，只在
"最后一条心跳恰好落在 8 秒窗口内"时才真丢。

**三个方案，需方定一个**：

| | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 规则 2 的 8s 闸**只管周期心跳**；事件心跳走单独限额（每会话每分钟 ≤6 条） | 规则 2 要改，C16 规则编号对齐要跟着核 |
| **B** | 不动规则 2，接受"每会话最多丢 8 秒"，把这个数写进文档 | 最省事；尾部系统性少算 |
| **C** | 前端不发事件心跳，回到纯周期心跳 | 暂停期间又开始白发（需方明确要求去掉的正是这个） |

**推荐 A 的理由**：事件心跳的条数由用户操作频率天然限死，不是刷时长的载体；
而闸 ② 已经给了每条 delta 的物理上限，限流的目的（保护 Redis 与日志表）由条数上限达成即可。

## 6. ⚠ 待定案：PRD 那个 97% 指标会恒定报警

PRD F2-7：

> 心跳数据有效率 = 通过校验（间隔 ≥8s 且参数合法）的心跳数 / 总心跳数，**≥97%**（低于此值说明刷课或网络异常显著）

**实测有效率 48%。** 按事件心跳设计，这个指标**永远达不到 97%**，上线即恒报警——
**而恒报警等于没有报警**。

这是 F-115 那个形状的又一实例：**指标定义在事件心跳出现之前，它现在测的已经不是它声称测的东西。**

**建议**：口径改为**只统计周期心跳**，阈值保持 97%。选方案 A 时这一条是配套的；
选 B 时同样要改（否则那 12/23 照样把指标压到 50% 上下）。

## 7. 九条规则的当前状态

| # | 规则 | 状态 |
| --- | --- | --- |
| 1 | 凭证有效 | 不变。只校验 `X-Play-Token`，**不回库重跑授权判定**（F-106） |
| 2 | 间隔校验 | **见第 5 节待定案**。理由只剩限流——「防重复投递」那一半已随「报累计不报增量」失效 |
| 3 | 拖拽校验 | **已废止 · 墓碑**（F-113）。编号留空不复用，4~9 不上移 |
| 4 | 倍速不加速累计 | 不变。`playRate` 不参与计时 |
| 5 | 异常心跳丢弃 | 收窄至：未通过规则 2、或参数明显非法。**不得因规则 6 的判定结果扣时长** |
| 6 | 推进一致性 | **降级为只留痕**（F-113）。写 `vod_heartbeat_log`，不影响时长 |
| 7 | 并发课时数 ≤ 2 | 不变 |
| 8 | 时长封顶 | **已废止 · 墓碑**（需方 2026-08-22）。编号留空不复用，9 不上移 |
| 9 | 同课时会话择一 | 不变。接管时执行闸 ③ |

**时长封顶废止的影响面**：闸 ② 已给出物理上限，一整天累加不超过真实流逝时间，
**不会**放出"999 小时"。**失去的是一项**：10 分钟的视频累计出 8 小时将原样记录
（原 `3×duration` 会压到 30 分钟）。该数值意味着循环播放整晚或前端故障，
**此后不再有任何提示**。需方已知情并接受。

## 8. 存储

**Redis**

```
key   vod:hb:{studentId}:{lessonId}          TTL 24h
Hash  watchedDuration / maxPosition / lastPosition / watchStatus /
      lastHeartbeatTime / videoId / courseId / activeSessionId / sessionPlayedBase
脏集合 vod:hb:dirty
```

有效心跳**只写 Redis，不直接写库**。XXL-Job / Spring 双路径注册，60 秒一轮扫脏集合批量落盘。

**Redis 故障降级**（B46）：直写数据库（限流阈值内），超限返回失败、前端静默重试不打断播放；
恢复后对账 Redis 与库中进度**取大值**合并。

**待建列**

```sql
ALTER TABLE vod_watch_progress
  ADD COLUMN last_position INT NOT NULL DEFAULT 0 COMMENT '上次离开位置（秒，断点续播起点）';
```

**两个位置列**：`last_position` = 上次离开位置（断点续播起点）；
`max_position` = 历史最远触达位置。判读：时长 60 分钟 + `max_position` 10 分钟 = 反复看开头；
+ 58 分钟 = 正常看完。

## 10. 服务端告警

```java
if (delta > dt + 5) {
    log.warn("心跳累计值超出物理上限，已截断：sessionId={} 报={} 上限={}", sessionId, delta, dt + 5);
}
delta = Math.min(delta, dt + 5);
```

**信号取自服务端自己的钟。不引入客户端自报的降级标志**——
要虚报时长的调用方会把那个标志报成正常值。
（POC 里有个 `clampTicks` 是同类信号，**它留在 POC 当诊断字段，不进签名**。）

## 11. 验收判据

### 11.1 用例（每条对应一次已发生的故障或一条契约铁律）

| 场景 | 断言 |
| --- | --- |
| 前端上报负增量 | 闸 ① 挡住，`delta = 0` |
| 上报 500 秒而 Δt = 10 | 闸 ② 截到 15，**并有 WARN** |
| **锁屏虚增 34.8、Δt = 89** | **服务端照收 34.8** |
| 换设备接管 | 基准置 0，时长继续增长 |
| 重发同一条心跳 | `delta = 0`，幂等 |
| 丢失一条心跳 | 下一条自动补回，不漏算 |
| 2 倍速播 5 分钟 | 记 5 分钟 |
| Redis 故障 | 降级直写库成功 |
| **事件心跳（Δt<8s）** | 按第 5 节定案断言 |

> **锁屏那条的断言方向是「照收」。** 它不是在验服务端的能力，
> 而是在**钉住"前端计时守卫是唯一防线、不可删除"这个事实**。
> 写成"服务端拦住"就等于给了后人删掉前端那层的理由。

### 11.2 变异

| 编号 | 变异 | 必须变红 |
| --- | --- | --- |
| M71 | 去掉闸 ① | 负增量 |
| M72 | 去掉闸 ② | 上报 500 秒 |
| M73 | 去掉闸 ③ 的基准重置 | 换设备接管 |
