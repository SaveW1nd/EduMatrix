## 2. 一条铁律

> **观看时长由前端算，服务端不算。服务端只做三件事：接收、限界、持久化。**

服务端任何地方重新计算时长即为缺陷。出现第二个时长来源，两份迟早分叉，
而分叉的表现是"两个页面显示的时长不一样"——**不报错**。

这条铁律派生出一个后果，实现时最容易违反：
**任何规则都不得以"本次不计时长"作为处置**。后端一旦这么做，就等于又在自己算时长。
规则 6 为此已降级为只留痕（见 §5）。

## 3. 接口 30 · 播放心跳上报

### 3.1 定义

```
POST /api/v1/vod/heartbeat
权限：student（仅累计本人进度）
请求头：Authorization + X-Play-Token（模块 12 §8.1 发放，TTL 300s）
```

**请求体（契约 §6.4 固定签名，任何字段不得增删改名；C15 核三处）**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `lessonId` | string | 是 | 课时 ID |
| `videoId` | string | 是 | 媒资 ID，须与课时当前关联一致 |
| `currentTime` | number | 是 | 当前播放位置（秒，一位小数） |
| `duration` | number | 是 | 播放器读到的视频总时长（秒） |
| `playRate` | number | 是 | 当前倍速（0.5~3.0）。**不参与计时**，仅落日志 |
| `seeked` | boolean | 是 | 拖动后 / 暂停恢复后的**第一次**心跳为 `true`，其余 `false`。缺失按 `false` 处理会让拖动后的心跳被判异常并污染日志 |
| `sessionId` | string | 是 | 本次播放会话 ID，取自 §8.1（续签不变） |
| `sessionPlayedSeconds` | integer | 是 | **本会话累计真播秒数**，前端计时器给出 |
| `trigger` | string | 是 | **本条心跳的触发原因**（F-116 新增，第 9 个字段）：`tick` / `pause` / `resume` / `ended` / `leave`。`tick` = 周期心跳，其余为事件心跳。**缺失或非法按规则 5 丢弃，不得默认成 `tick`** |

**响应体（固定签名）**

```json
{ "code": 200, "msg": "操作成功",
  "data": { "watchedDuration": 130, "watchStatus": 1, "maxPosition": 135 } }
```

**错误码**

| 码 | 含义 | 客户端行为 |
| --- | --- | --- |
| 20001 | 凭证过期或无效 | 无感调 §8.1 续签后重试，播放不中断 |
| 20002 | 心跳被丢弃 | **静默降级**，不弹窗、不打断播放、不回退进度条；连续 3 次仅上报监控埋点 |
| 20014 | 课时不存在或不可见 | 停止播放 |
| 20020 | 该课时正在其他设备播放 | **暂停并提示**，给「在本设备继续」按钮（点击后停报 60s 等待接管）。**不得静默降级** |

### 3.2 前端在什么时候上报

**每次都报【当前累计值】，不是增量。**

| # | 触发时机 | `trigger` 取值 | 类型 |
| --- | --- | --- | --- |
| 1 | 正在播放时，每 **10 秒** | `tick` | 周期 |
| 2 | **停下来那一刻**：`pause` / `waiting` / `seeking` | `pause` | 事件 |
| 3 | **恢复播放那一刻**：`play` / `seeked` | `resume` | 事件 |
| 4 | **播完**：`ended` | `ended` | 事件 |
| 5 | **离开页面**：`pagehide`，用 `sendBeacon` 发 | `leave` | 事件 |
| 6 | 停表期间 | — | **不发** |

**为什么报累计值不报增量**——三条都被真机验过：
- iOS 实测有 12 条心跳被**重复投递**。报增量会凭空多出 120 秒；报累计值时同一个值再来一次 `delta = 0`，天然幂等。
- 页面被冻结期间丢包不影响正确性，下一条自动补回。
- 正因如此，停表期间才可以放心地不发。

**第 4 条是唯一没有下一条来补的心跳**，必须用 `sendBeacon`（`fetch` 在页面卸载时会被取消）。

**`ended` 必须发**：它带着最终累计值，播完之后不会再有任何心跳。

**长时间暂停与凭证 TTL**：`X-Play-Token` TTL 300 秒。学生暂停超过 5 分钟再恢复，
恢复那条心跳会拿到 `20001`。**前端在恢复播放前先续签，不要等被拒再补**——
等被拒再补会丢掉恢复后的第一条，而那条正好带着暂停前的尾巴。

### 3.3 服务端处理流程

```
① 校验 X-Play-Token（规则 1）           不通过 → 20001，直接返回，不写日志
② 取会话（规则 9）                       冲突 → 20020，不计时长、不推进任何基准
③ 间隔与参数校验（规则 2、5）            不通过 → 20002，写日志，不推进任何基准
④ 算 delta（三道闸，见 §4）
⑤ 写 Redis + 加入脏集合
⑥ 写 vod_heartbeat_log（每条都写）
⑦ 返回 watchedDuration / watchStatus / maxPosition（合并 Redis 与 DB 取大值）
```

**被拒绝的心跳一律不推进任何基准**：规则 2 的时间基准、规则 6 的位置基准、
`maxPosition`、`lastPosition`、`sessionPlayedBase`。
唯一例外是规则 9 的会话接管（见闸 ③）。

## 4. 三道闸

### 闸 ① 非负

```
delta = max(0, 本次 sessionPlayedSeconds − sessionPlayedBase)
```

**拦的是**：前端算出负值。
**真实实例**：POC 计时二版按「视频前进量」计时，往回拖时算出 **−240 秒**。

### 闸 ② 物理上限

```
Δt    = 本次与【上一次被采纳心跳】的服务端接收时间差
delta = min(delta, Δt + 5)
```

**拦的是**：数量级错误与伪造。上报 500 秒而服务端只过了 10 秒 → 截到 15。

**⚠ 它不拦锁屏虚增。这段实测必须写进代码注释：**

```
POC 计时一版，安卓，锁屏 5 分半再解锁：
  上一条心跳 10:57:57   sessionPlayedSeconds = 61
  本条心跳   10:59:26   sessionPlayedSeconds = 95.8
  Δt = 89 秒   天花板 = 94   虚增 34.8 < 94   →   原样收下
锁屏期间心跳照发（一版的定时器空转），Δt 随之增大，虚增始终在天花板之下。
```

**缺这段注释的后果**：后续维护者以为本闸防锁屏，进而删掉前端的计时守卫——
而那一层是这类虚增的**唯一防线**。

**截断发生时写 `vod_heartbeat_log` 留痕，不占用 `reject_rule`**（心跳被采纳了，只是增量被削），
并打一条 WARN（见 §7）。

### 闸 ③ 会话接管时基准置零

会话接管（原活跃会话 60 秒无有效心跳）时，**同时**重置：规则 6 的位置基准、
**`sessionPlayedBase` → 0**。

**拦的是**：时长永久冻结。不重置时，新设备第一条心跳的累计值小于上一端，
`delta = max(0, 负数) = 0` 恒成立，**时长永不增长且不报错**。

## 5. 九条规则的当前状态

| # | 规则 | 状态与处置 |
| --- | --- | --- |
| 1 | 凭证有效 | 只校验 `X-Play-Token` 本身，**不回库重跑授权判定**（F-106 定案）。要更快生效不必查库：撤销时主动删掉受影响学生的 `play:auth` 键即可 |
| 2 | 间隔校验 | **按 `trigger` 分流（F-116）**：`tick` 走 8 秒闸（Δt<8s 判异常走规则 5）；**事件心跳一律采纳、不做任何间隔限制**。异常明细每会话每分钟限 20 条。**理由只剩限流**（挡高频空包、保护 Redis 与日志表）。详见 §6 |
| 3 | 拖拽校验 | **已废止 · 墓碑**（F-113）。编号不写入 `reject_rule`、不复用，4~9 不上移 |
| 4 | 倍速不加速累计 | `playRate` 不参与计时。**注意口径已变**：原文写"按服务端墙钟间隔计算"，F-113 后时长来自前端，本条现在的含义是**服务端不得用 `playRate` 去调整前端报来的值** |
| 5 | 异常心跳丢弃 | 未通过规则 2，或参数非法（`currentTime` 越界、`duration` 与媒资偏差 >5%、`playRate` 越界、`sessionPlayedSeconds` 为负/非整数/缺失）→ 丢弃 + `20002`，明细仍写日志。**不得因规则 6 的判定结果扣时长** |
| 6 | 推进一致性 | **降级为只留痕**：判定逻辑不变（连续两次 `seeked=false` 之间，`Δ currentTime` 须落在 `[0.5,1.5]×Δt×playRate`），命中时只写 `reject_rule=6`，**心跳仍被采纳、时长照算**。`seeked` 滥用防护：连续 `true` ≤2 次、单课时每小时 ≤180 次 |
| 7 | 并发课时数 ≤ 2 | 活跃 = 60s 内有有效心跳。超出直接丢弃并计 `reject_rule=7` |
| 8 | 时长封顶 | **已废止 · 墓碑**（需方 2026-08-22）。编号留空不复用，9 不上移 |
| 9 | 同课时会话择一 | 同会话正常；不同会话且当前会话 60s 内活跃 → `20020`；超 60s 无心跳 → **新会话接管，执行闸 ③** |

**`reject_rule` 取值域**：0 采纳，2/5/6/7/9 = 被对应规则命中。
**1、3、4、8 保留不使用**——规则 1 在写日志之前就返回了；3 与 8 是墓碑；4 是计时口径不拒绝心跳。

**时长封顶废止的影响面**：闸 ② 已给出物理上限，一整天累加不超过真实流逝时间，
**不会**放出"999 小时"。**失去的是一项**：10 分钟的视频累计出 8 小时将原样记录
（原 `duration×3` 会压到 30 分钟）。该数值意味着循环播放整晚或前端故障，
**此后不再有任何提示**。需方已知情并接受。

## 6. 心跳限流（F-116 定案）

### 6.1 规则

```
trigger = tick（周期心跳）
    Δt = 与上一次【被采纳】心跳的服务端接收时间差
         （首次心跳以凭证发放时间为锚点）
    Δt ≥ 8s  → 有效
    Δt < 8s  → 异常，走规则 5：丢弃 + 20002，reject_rule = 2

trigger ≠ tick（事件心跳 pause / resume / ended / leave）
    → 一律采纳，【不做任何间隔限制】

异常心跳的日志限流（保护 vod_heartbeat_log）
    每会话每分钟最多写 20 条异常明细
    第 21 条：写一条汇总行（reject_rule=2，备注"本分钟异常已达 20 条，后续静默丢弃"）
    第 22 条起：仍然拒绝并返回 20002，但【不再写明细】
    精确条数看指标 heartbeat_reject_total{rule}（契约 §7.1）
```

### 6.2 为什么事件心跳不设上限

§3.2 的**事件心跳本来就不看表**——学生第 55 秒按暂停，而上一条周期心跳在第 50 秒，
间隔才 5 秒。硬 8 秒闸会把它判为异常丢掉。

大多数情况不要紧（报累计值，下一条会补上）。**但如果他暂停后直接关页面，就没有下一条了。**

**真机实测**（把 24 条心跳喂给硬 8 秒闸）：

```
被丢 12 条 / 共 23 条（52%）
服务端入库 69.3 秒   前端报 76.3 秒   →   差 7.0 秒
丢的 7 秒在【最后一条暂停心跳】上，它之后没有任何心跳来补
```

**事件心跳的条数由用户操作频率天然限死**——学生暂停几次就几条，一次观看也就十几条，
**不是刷时长的载体**；而闸 ② 已经给了每条 delta 的物理上限。
**限流的对象是周期心跳与高频空包，不是事件心跳。**

### 6.3 为什么必须加 `trigger` 字段

服务端**无法从原来那 8 个字段分辨心跳类型**：

```
lessonId  videoId  currentTime  duration  playRate  seeked  sessionId  sessionPlayedSeconds
```

`seeked` 只在"拖动后 / 恢复后第一条"为 `true`——**盖不住暂停、盖不住离开页面**，
而且它的语义是另一件事（重置规则 6 的推进基准）。

**用枚举不用布尔**：`trigger` 会落进 `vod_heartbeat_log`，**顺带说明每条心跳是为什么来的**。
布尔只能答"是不是周期的"，枚举能答"学生当时在干什么"——而**日志是第一版唯一的行为事实来源**。

**这是心跳签名第四次变更**（前三次：`seeked` 解 seek 复看被误判、`sessionId` 解多端并发永久归零、
`sessionPlayedSeconds` 改前端计时），C15 核的三处已同步。

**⚠ `trigger` 缺失或取值非法一律按规则 5 丢弃，不得默认成 `tick`。**
默认成 `tick` 会让事件心跳重新被卡在 8 秒闸上，**等于这条定案没做，而且不报错**。

### 6.4 实现细则

| # | 项 | 定法 |
| --- | --- | --- |
| 1 | 分流依据 | **只看 `trigger`**，不做任何推断 |
| 2 | 异常计数维度 | 按 `sessionId` + 分钟（`epochSecond / 60` 固定分桶） |
| 3 | Redis key | `vod:hb:err:{sessionId}:{epochMinute}`，TTL 120s |
| 4 | 原子计数 | `INCR`；返回 1 时设 TTL；返回 21 时写汇总行；> 21 不写明细 |
| 5 | 被拒的心跳 | **不推进任何基准**（含"上次被采纳"的时间基准） |
| 6 | Redis 不可用时 | **不做异常计数，异常明细照写库**（走 §8.4 降级路径） |

**为什么取固定分钟窗口而不是滑动窗口**：滑动窗口要为每个会话存一串时间戳，
**为了保护日志表反而给 Redis 加负担**。边界处最多多写 20 条明细，对这个目的毫无威胁。

**第 5 条是不会卡死的保证**：周期心跳被拒 → 不推进基准 → 下一条的 Δt 从更早那条继续算
→ 自然涨到 ≥8s → 必被采纳。**最坏情况只是延迟，不是永久拒绝。**

### 6.5 心跳数据有效率指标的口径

PRD F2-7 的「心跳数据有效率 ≥97%」，**口径为只统计 `trigger = tick` 的周期心跳**，阈值不动。

**为什么必须限定**：事件心跳一律采纳、从不进入"异常"，把它们算进分母会让这个比值
**恒定偏高而失去意义**；而在按 `trigger` 分流之前的设计下，实测有效率是 **48%**——
那时它**上线即恒定报警，而恒报警等于没有报警**。

指标说明里的「刷课或网络异常显著」一并改为「网络异常显著」——
「刷课」那半个理由随 F-113 已经不成立。

## 7. 服务端告警

```java
if (delta > dt + 5) {
    log.warn("心跳累计值超出物理上限，已截断：sessionId={} 报={} 上限={}",
             sessionId, delta, dt + 5);
}
delta = Math.min(delta, dt + 5);
```

**信号取自服务端自己的钟，不引入客户端自报的降级标志**——
要虚报时长的调用方会把那个标志报成正常值。

## 8. 存储

### 8.1 Redis

```
key    vod:hb:{studentId}:{lessonId}          TTL 24h
Hash   watchedDuration / maxPosition / lastPosition / watchStatus /
       lastHeartbeatTime / videoId / courseId / activeSessionId / sessionPlayedBase
脏集合  vod:hb:dirty

异常计数 vod:hb:err:{sessionId}:{epochMinute}   TTL 120s，值为该分钟内的异常心跳条数
```

`sessionPlayedBase` = 该会话上一次上报的 `sessionPlayedSeconds`，用来算 `delta`；**闸 ③ 时置 0**。

**有效心跳只写 Redis，不直接写库。**

### 8.2 位置字段推进

```
maxPosition  = max(maxPosition, currentTime)     // 历史最远触达
lastPosition = currentTime                        // 直写不取大，供断点续播
```

`maxPosition` 的更新动作原属规则 3，规则 3 废止后动作本身保留，移到这里。

### 8.3 批量落盘

XXL-Job / Spring 双路径注册，**60 秒一轮**扫脏集合，批量 UPSERT `vod_watch_progress`
（UK `student_id + lesson_id`），心跳明细批量插入 `vod_heartbeat_log`（按月分区），
落盘成功后移出脏集合。实例宕机最多丢 60 秒增量，可接受。

### 8.4 Redis 故障降级（B46）

直写数据库（限流阈值内），超限返回失败、前端静默重试不打断播放；
故障恢复后对账 Redis 与库中进度**取大值**合并。

### 8.5 迁移

```sql
ALTER TABLE vod_watch_progress
  ADD COLUMN last_position INT NOT NULL DEFAULT 0 COMMENT '上次离开位置（秒，断点续播起点）';
```

类型取 `INT`，与 `max_position` 一致。

**两个位置列的分工**：`last_position` = 上次离开位置（断点续播起点）；
`max_position` = 历史最远触达位置。判读：时长 60 分钟 + `max_position` 10 分钟 = 反复看开头；
+ 58 分钟 = 正常看完。

## 9. 接口 31 · 单课时进度

```
GET /api/v1/vod/progress?lessonId={lessonId}
权限：student（仅本人）。管理端不开放，教师/管理员走 /api/v1/stat/**
```

合并 Redis 缓冲与 `vod_watch_progress`**取大值**返回，保证准实时。
**无任何记录时返回全零的「未开始」态，不报错。**

```json
{ "code": 200, "msg": "操作成功",
  "data": { "lessonId": "...", "videoId": "...", "courseId": "...",
            "duration": 600, "watchedDuration": 130, "maxPosition": 135,
            "watchStatus": 1, "completeTime": null,
            "lastHeartbeatTime": "2026-08-12 10:23:45" } }
```

**错误码**：20014。

**本接口不加授权校验**（F-48 已定案，需方 2026-08-21）：与「学生端保持两种回答」同源，

## 11. 验收判据

### 11.1 用例（每条对应一次已发生的故障或一条契约铁律）

| 场景 | 断言 |
| --- | --- |
| 上报负增量 | 闸 ① 挡住，`delta = 0` |
| 上报 500 秒而 Δt = 10 | 闸 ② 截到 15，**且有 WARN** |
| **锁屏虚增 34.8、Δt = 89** | **服务端照收 34.8** |
| 换设备接管 | 基准置 0，时长继续增长 |
| 重发同一条心跳 | `delta = 0`，幂等 |
| 丢失一条心跳 | 下一条自动补回，不漏算 |
| 2 倍速播 5 分钟 | 记 5 分钟 |
| 同一课时两端同时播 | 后到的拿 `20020`，时长不双算 |
| 并发第 3 个课时 | 丢弃，`reject_rule=7` |
| 规则 6 命中 | **心跳仍被采纳、时长照算**，只写 `reject_rule=6` |
| Redis 故障 | 降级直写库成功 |
| **事件心跳，Δt=0** | **被采纳**，时长照算（不受任何间隔限制）|
| 周期心跳 Δt=5s | 异常 → `20002`，`reject_rule=2` |
| 周期心跳连续被拒 | Δt 持续增长，**最终必被采纳**，不永久卡死 |
| 一分钟内第 21 条异常 | 写一条汇总行；第 22 条起**仍拒绝但不写明细** |
| `trigger` 缺失 / 取值非法 | 按规则 5 丢弃，**不得默认成 `tick`** |

> **锁屏那条的断言方向是「照收」。** 它不是在验服务端的能力，
> 而是钉住"**前端计时守卫是唯一防线、不可删除**"这个事实。
> 写成"服务端拦住"就等于给了后人删掉前端那层的理由。
