## 2. 观看时长：前端算，后端收

### 2.1 谁算

**需方定案：「前端写计时器其实没关系」。**

于是原设计里「后端按心跳到达间隔累加 `min(Δt, 15)` 秒」**整套不做**。后端从"计时者"退成"记账者"。

### 2.2 前端计时有三个坑，逐字写死

#### 坑一 · 累计的是**墙钟**，不是媒体时间

| 写法 | 2 倍速播 5 分钟 | 判定 |
| --- | --- | --- |
| 累计**真实经过的时间** | 算 **5 分钟** | ✅ 符合规则 4 |
| 累计 `currentTime` 的**增量** | 算 **10 分钟** | ❌ 违反规则 4 |

**第二种是更容易想到的写法**——监听 `timeupdate`、把 `currentTime` 的增量加起来，代码更短、看上去更"准"。而它会让**倍速自动加速计时**，正好推翻规则 4「倍速不加速计时」。

**实现约束（逐字写进 PRD F2-7 与 03-03 §8.3）**：
> 计时器累计的是**播放状态持续的真实时间**（墙钟），**不是 `currentTime` 的增量**。
> 只在 `playing` 且页面可见时走表；`pause` / `waiting` / 页面隐藏时停表。
> **`playRate` 不参与计时**，它只作为报文字段上报。

#### 坑二 · 报**累计值**，不报增量

| 上报什么 | 网络重发 | 丢一个包 |
| --- | --- | --- |
| 增量「这 10 秒我播了 8 秒」 | **多算一次** | **永远少算** |
| 累计「本会话至今共播 N 秒」 | 无害（同一个数） | **下次自动补回** |

**定为累计值。** 服务端：

```
delta = max(0, 本次 sessionPlayedSeconds − 该会话上次 sessionPlayedSeconds)
watched_duration += delta
```

- **重发天然幂等**：同一个累计值再来一次，`delta = 0`。
- **丢包自愈**：丢的那次的量，下一次的累计值里带着。
- **页面刷新 = 新会话**，累计从 0 重起；服务端按 `sessionId` 分别记基准，与规则 9（同课时会话择一）配合处理多设备。**会话接管时基准重置为 0**，否则新设备第一条心跳会因为"累计值比上一端小"而 `delta = 0` 一直不涨。

**连带：规则 2 的理由要删掉一半。** 规则 2「间隔 <8s 丢弃」原本有两个理由——限流、**防重复投递把时长算两遍**。改报累计之后**后一个理由不成立了**（重发幂等）。**规则保留**（限流仍然有用，且能挡住高频空包），**但把失效的那半个理由删掉**——不要留着一条理由已经不对的规则。

#### 坑三 · 服务端仍要做**物理上限截断**，当 bug 兜底

浏览器会**冻结后台标签页的定时器**。页面从后台醒来时，一个写得糙的计时器可能一口气报出几小时。**这不是作弊，是前端 bug**——而它会污染报表。

```
delta = min(delta, Δt + 5)        // Δt = 两次心跳的服务端接收时间差
```

**必须写明它是上界，不是第二个真相**：服务端不重新计算时长，只拒绝接受"物理上不可能"的增量。**一个数、一个封顶，不构成两个数字打架**——这正是本项目反复吃亏的形态，写清楚是为了让下一个人不要把它"补全"成第二套计时。

截断发生时写 `vod_heartbeat_log` 留痕（**不占用 `reject_rule`**：心跳被采纳了，只是增量被削），供排查前端计时器 bug。

**规则 8（单日 10h / 单课时 3×duration）同样保留，理由由「防刷」改为「兜 bug」。**

### 2.3 心跳报文签名变更（明知的契约变更，登记）

契约 §6.4 标题写着「最高频接口，**签名固定**」。**本次是对它的推翻，不是补充**，写明如下：

### 3.1 规则 3（拖拽校验）废止 → 墓碑

放开拖动后本条失去对象。照 §8.2 接口 29 的先例：

- 规则表**保留 3 号行**，写明「已废止（F-113）」与理由；
- **编号 3 从此不写入 `reject_rule`，且不得复用**；
- **4~9 号不上移**（全库大量交叉引用，重编号收益为零而指错了没有任何症状）；
- **同时删除表下方那段注记「规则 3 与 `seeked` 无关」**——它论证的是「若对 seek 心跳放开规则 3，禁快进就被绕过」，规则 3 没了，论证的对象也没了。

### 3.2 ⚠ 规则 6 降级为只留痕（本轮最容易实现错的一条）

**判定逻辑不变**：连续两次 `seeked = false` 的心跳之间，`Δ currentTime` 须落在 `[0.5, 1.5] × Δt × playRate`。

**处置变了**：

```
原：检测到异常 → 本次【不计入 watchedDuration】     ← 后端在算时长
新：检测到异常 → 【只写 vod_heartbeat_log 留痕】     ← 后端只记账
```

**为什么必须这样**：时长既然由前端给，后端一旦说「这条我不给你算」，**后端就等于又在自己算时长**——那就变回**两个数字表示同一件事**，本项目反复吃亏的形态。

**`seeked` 每小时上限 20 → 180**（需方定案三）。连续上限 **2 次维持不变**。

**上限保护的对象也变了，理由要写实**：

```
原：防止脚本恒置 seeked=true 从而永久关闭规则 6，【保护时长的准确性】
新：防止脚本恒置 seeked=true 让规则 6 永不判定，【保护日志的诊断价值】
```

时长已经不由规则 6 决定了，所以它保护不了时长。它保护的是「`vod_heartbeat_log` 里还能看出这个学生有没有在真的播放」——**日志是第一版唯一的行为事实来源**。

### 3.3 规则 5 收窄：只丢参数非法，不得因规则 6 扣时长

**只丢弃「参数明显非法」的报文**：

- `currentTime ∉ [0, duration + 2]`
- `duration` 与 `vod_video.duration` 偏差 > 5%
- `playRate ∉ [0.5, 3.0]`
- **`sessionPlayedSeconds` 为负、非整数、或缺失**（新增）

**明确禁止**：不得因为规则 6 的判定结果去扣时长。规则 2 失败仍丢弃（限流），规则 3 已废止不再是丢弃理由。

## 4. 完播判定：延后，且**将来也不回算**

**需方定案四原话**：「我们不会重算的，如果后续要，也只会要每个学生在那堂课上花了多少时间」。

**那个数第一版就在存**：`vod_watch_progress.watched_duration`，逐 `student_id` + `lesson_id`，**从模块 13 上线那天起**。不需要任何额外工作。

第一版 `watch_status` 只在 0（未开始）/ 1（学习中）之间流转，**不写 2**；`complete_time` 恒空。

### 4.1 「可回算、无历史空洞」这句话要改准

原提案说「跑批任务就能全部回算补上，历史不丢」——**这句话对一半**：

| | 能不能补 |
| --- | --- |
| **完播状态**（某学生某课时到底算不算完成） | ✅ 能。`watched_duration` 是终值，随时比一次阈值就出来 |
| **每日历史序列**（`stat_*_daily` 里逐天的完播数） | ⚠ **只能靠重放 `vod_heartbeat_log` 补**，且**只能补到该表保留期为止**（按月分区留 6 个月） |

**但需方已定不回算**，所以此处**只作事实记录，不是待办**。

### 4.2 已有资产，不用新建

| 东西 | 位置 | 状态 |
| --- | --- | --- |
| `complete_rate_threshold` | `common/tenantconfig/TenantConfigKey.java:39` | **已实现**，默认 90，范围 60~100 |
| 租户配置校验 | `system/tenant/service/TenantConfigService.java:99` | **已实现** |
| `watch_status` / `complete_time` | `vod_watch_progress` 表 | 表结构里已有，留空不写 |

**`TenantConfigKey` 的 Javadoc 要加一句**：该处写着「修改只影响此后的判定，存量不回溯重算」，与"将来开完播"的字面读感打架（一个说改阈值、一个说开功能）。需方已定**不回算**，加一句写明本项目不做完播回算，两句不冲突。

### 4.3 第一版没有完播率的下游，逐条点名

**不是"以后再补数据"，是第一版没有这些指标**：

- 导师看板（F4-1）头号 KPI「名下学员平均完播率」

- **北极星指标本身**（PRD §88「名下学员平均完播率」）——**第一版没有北极星指标**，这一条要在 PRD 里写明，不能让它悬着

**统计表那几列第一版恒为 0**（`finished_lesson_count` / `avg_complete_rate` 等），而**那个 0 与「真的一个都没完播」逐字节相同**。需方明确表示无所谓（不看那个趋势图）。**因此不做"启用日期"机制**，只在 `02-数据库设计` 相应列旁写一句：

## 5. 内容覆盖率不做 —— 代价比原估计小得多

覆盖率（记录"具体看过哪些片段"）**不做**。

**原提案说它唯一能多抓到的场景**：学生把前 10 分钟**反复看 6 遍** = 时长 60 分钟（看着达标），实际只看了六分之一。

**这个场景其实是可识别的，用一个已经在存的数——`max_position`：**

| 观察到 | 判读 |
| --- | --- |
| 时长 60 分钟 + `max_position` **10 分钟** | **一直在看开头** |
| 时长 60 分钟 + `max_position` **58 分钟** | 正常看完 |

**不用做覆盖率、不加任何字段、这个数第一版就在存。** 它是近似（认不出中间跳过的片段），但恰好认得出原提案点名的那个唯一场景。

**因此覆盖率的代价重估为：小。** 仍然存在的真空洞是——**精确的内容覆盖度**（哪几段没看）永远补不回来，因为它需要自己的原始数据。若将来要，只能从开启那天起统计。**登记为已知取舍，不是待办。**

> **诚实边界（需方已接受）**：时长、`max_position`、覆盖率**都挡不住**"挂机让它自己播完"。这与定案零一致。

## 8. 建表改动：只有一列，且必须是 INT —— **但本轮不建**

`vod_watch_progress` **待新增**（ALTER 语句登记在 `02-数据库设计` §4.2.7 的「待建列」块，**本轮不执行**）：

```sql
last_position INT NOT NULL DEFAULT 0 COMMENT '上次离开位置（秒）'
```

**必须是 INT，不能是 DECIMAL**：`max_position` 是老列、类型 `INT`、**改不了**。两列都表示"视频里的某个位置"，**精度不同会让「上次离开的位置是不是就是最远位置」这类判断永远为假且不报错**——这是最坏的一类缺陷。**新列跟旧列走。**

**用途**：F2-8 断点续播的起点。原设计取 `max_position`（最远触达），放开拖动后那可能只是学生随手拖到过的位置，**从那里续播会跳过他实际没看的中间部分**。

**⚠ 本轮为什么不建**：模块 13 未开工、`backend/` 本轮零改动（除一处 Javadoc）。而 **C14 核「DDL 列集合 = 文档字段表」**——先把该列写进字段表会立刻报 `文档字段表有而 DDL 缺 [last_position]`（**实测报过**）。故照 **F-12「落地脚本」先例**：ALTER 语句先登记，字段表等模块 13 的迁移执行后再补。
