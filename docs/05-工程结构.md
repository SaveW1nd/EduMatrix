# EduMatrix 工程结构（代码仓库的目录与包规划）

> **本文档定的是"代码放哪"，不定"代码做什么"。** 后者在 `04-实施计划.md`：17 个模块各自的表、接口、规则与验收标准。
>
> **文档权威顺序**（同 `04-实施计划.md` 首段）：`DESIGN-CONTRACT.md` > `03-API接口文档/` 六分册 > `01-PRD-产品需求文档.md` > `02-数据库设计.md` + 基线 DDL。本文档在这条链之下——**它不产生新的约束，只把已有约束落到目录上**。若本文与上述任一文档冲突，以上述为准。
>
> **为什么现在写**：仓库当前 19 个文件、0 行代码。一个开发者按 01 → 17 顺序推进，每个模块可能交给不同的 Agent 执行。没有统一目录约定，第 5 个模块和第 12 个模块会长成两种样子；而模块 01 交付的公共层被其余 16 个模块 import，**包路径定错一次就是全库替换**。

## §A 三个选型问题

### A1 单模块 Maven，不拆多模块

**结论：一个 `backend/pom.xml`，一个 `src/main/java`。**

参考仓库 RuoYi-Vue-Plus 是多模块，但那是**多人并行**的产物：module 边界在那里的作用是"你不能 import 我的内部类"，而这条约束只有在"你"和"我"是两个人时才需要机器来执行。

本项目的实际风险方向是**相反的**：

| | 多人协作项目 | 本项目（单人 + 单模块 Agent） |
| --- | --- | --- |
| 要防的事 | B 组乱 import A 组内部实现 | 模块 12 的 Agent **没看见**公共层，自己又写了一个子树查询 |
| 多模块的作用 | 有效——编译期就拦住 | **反向有害**——import 公共层需要先改 pom，摩擦越大越容易"就地再写一个" |

模块 01 的禁止事项已经明写「不重写公共层：后续模块需要上述能力时**调用这里的类**」。多模块把"调用"这件事变贵，正好和这条要求相抵。

**代价与处置**：单模块下没有编译期的分层护栏。处置不是引入构建工具，而是三条可 grep 的硬约束（同模块 01「做完什么算做完」的自检风格）：

```bash
# ① 业务包不得出现手写租户放行条件（模块 01 已有此项自检）
grep -rn "OR tenant_id = 0" backend/src/main/java --include=*.java        # 期望 0 行

# ② 业务 Mapper 不得出现 FIND_IN_SET（模块 01 已有此项自检）
grep -rn "FIND_IN_SET" backend/src/main/resources/mapper                  # 期望 0 行

# ③ 领域包不得互相 import（本文新增的约定）
grep -rnE "^import com\.edumatrix\.(org|course|vod|question|homework|stat)\." \
     backend/src/main/java/com/edumatrix/vod                              # 期望 0 行；八个领域各查一次
```

第三条是本文新增的**约定**，不是新约束——它只是把"领域之间不互相摸实现"写成可执行的检查。

**跨领域读取的正确形态：接口声明在 `common/`、实现在提供方领域内、消费方按接口注入。**

> **〔订正，模块 08 落地时发现〕** 本段原写「跨领域读取一律走对方领域的 Service（例：模块 08 校验课时关联时读 `vod_video`，调 `vod` 领域的 Service，不直接注入 `VodVideoMapper`）」——**照字面做必然红**：注入对方领域的 Service 同样要写 `import com.edumatrix.vod.…`，而检查③ 拦的是 **import 语句**，它不区分 Service / Mapper / 实体。模块 07 已实测踩过一次（org → system），当时的处置就是下面这条路径，只是没回写到本节。
>
> 既有先例：`common/account/PasswordHasher` + `common/account/SessionRevoker`（接口）↔ `auth/session/AuthAccountProvider`（实现）↔ `system` / `org`（消费方）。模块 08 沿用同一形态：`common/media/VideoRefReader` ↔ `vod`（模块 09 落地后）、`common/file/InlineFileUrlProvider` ↔ `system/file/SystemFileProvider`、`common/subtree/CurrentNodeProvider` ↔ `org/node/CurrentNodeResolver`。
>
> **`common/` 不进检查③ 的扫描范围**（脚本只遍历八个领域包），且领域包 import `common` 本就合法——这正是它能当交汇点的原因。

**什么时候该拆**：出现第二个可独立部署的进程时（例如把 XXL-Job 执行器单独打包）。在那之前拆是提前支付成本。

### A2 按领域一级、分层二级

**结论：`com.edumatrix.<领域>.<子域>.{controller,service,mapper,entity,dto,vo}`。领域名 = 契约 §6.2 的八个路由前缀，一个不多一个不少。**

对比：

| | 分层一级（`controller/` 下放全部 Controller） | **领域一级（本方案）** |
| --- | --- | --- |
| Agent 拿到「做模块 07」的工单 | 要在 5 个顶层目录里各找一遍，改动散在 5 棵树 | 改动集中在 `org/member/` 一棵子树 |
| 两个模块同时落在同一层 | `service/` 目录混着 17 个模块的实现类 | 各自在自己的子域包里 |
| 从 URL 反推代码位置 | 推不出来 | `/api/v1/org/students/{id}` → `com.edumatrix.org.member` |

第三行是选它的主要理由：**契约 §6.2 已经把系统按领域切了一刀，这一刀是权威的**。让包结构与它同构，URL 与代码位置互相可推——这是 Agent 定位文件最省事的方式，也让「不自造领域名」这条纪律有了物理载体（想造新领域名，得先在契约 §6.2 加一行）。

**领域内为什么还要子域**：`/api/v1/org/**` 一个前缀承载 50 个接口、横跨模块 06/07/11/17。全部平铺在 `org/controller/` 下是 50 个类一个目录。子域按**名词**切（`node` / `member` / `grant` / `template` / `tag` / `dataimport`），不按模块编号切——模块编号是一次性的施工顺序，名词是长期的。

### A3 前端两个独立工程，不做 monorepo

**结论：`frontend-admin/`（PC 管理端 + 教师端）与 `frontend-h5/`（学生端），两个独立的 npm 工程，各自 `package.json`、各自构建、各自部署。**

页面归属（PRD §6.1 / §6.2 / §6.3）：A1–A22（管理端 22 页）+ B1–B13（教师端 13 页）落 `frontend-admin`；C1–C12（学生端 12 页）落 `frontend-h5`。

四条理由，按分量排序：

1. **依赖集完全不相交。** 管理端要 Element Plus（表格、树、表单、抽屉）；学生端 12 个页面里没有一个需要它，却要 DPlayer + hls.js（`frontend-admin` 只在媒资预览用得到播放器，且不需要禁快进与水印那套二开）。合成一个工程后，两边的依赖都会进对方的 `node_modules`，而**学生端恰好是最不能胖的那一端**——PRD §7.4 把微信内置浏览器（X5/XWEB）列为一级适配目标。
2. **PRD §7.5 第 5 条要求学生端能力可被小程序复用**（无 Cookie 依赖、无浏览器特有 API 依赖）。它是一个**将来要被整体搬走**的东西。与管理端共处一个工程，搬走时要先做拆分；独立工程时，搬走 = 换一层渲染。
3. **鉴权拓扑不同。** 管理端全部请求走 `Authorization: Bearer`；学生端除此之外还有一条**播放器内核发起、不带任何自定义头**的请求（`GET /api/v1/vod/decrypt-key`，00-通用约定 §2.3）。它不经过前端的 axios 实例，因此**前端的统一请求封装对它完全无效**——这条链路只存在于 `frontend-h5`，把它和管理端的请求层混在一起只会让人误以为拦截器能管到它。
4. **发布节奏不同。** 学生端 12 个页面基本由模块 14 一次做完；管理端 35 个页面从模块 03 铺到模块 17。合一个工程意味着模块 03 的一次改动要连带回归学生端构建。

**代价：请求封装会重复一份**（响应体 `{code,msg,data}` 拆包、业务错误统一 HTTP 200 的处理、bigint ID 字符串化、`X-Trace-Id` 回显——`00-通用约定` §3 / §5）。约 150 行。

**不为这 150 行引入 pnpm workspace**：workspace 的成本不是配置文件，是每次加依赖都要回答"装到哪个 package"——这与 A1 拒绝多模块 Maven 是同一笔账。代价的处置是**把重复的部分列清楚**，让它别悄悄分叉：

| 两端必须一致的东西 | 依据 |
| --- | --- |
| 响应体拆包与业务错误处理（HTTP 200 + `code`） | `00-通用约定` §3 / §3.3 |
| bigint ID 一律按字符串收发 | `00-通用约定` §5 |
| 时间格式与东八区 | `00-通用约定` §6、契约 §6.1 |
| `X-Trace-Id` 从响应头取出并在报错提示中展示 | 契约 §7.1 |

这四行改动时**两个工程都要改**——写在这里，是因为下一个人只会改他手上那一个。

## §B `docs/sql/` 的归属：选 A（全部迁走）

### B1 现状与三条路

当前 `docs/sql/` 混着两种身份的文件：

| 文件 | 身份 |

| 方案 | 判断 |
| --- | --- |
| **A 全部迁进 `db/migration/`，基线改名，`docs/sql/` 清空** | **选它** |
| B 留在 `docs/`，Flyway 用 `filesystem:` 指过去 | **不可行**。`filesystem:` 解析的是运行时工作目录下的真实路径，打成 jar 部署到服务器上 `docs/` 不存在，启动即失败。要规避只能把 `docs/` 一起打进发布包——那等于把 1.7 万行设计文档塞进生产制品 |

**选 A 的正面理由**（不只是"另外两条不行"）：契约 §7.3 已经宣布这个文件**就是**基线。一个文件只有一个身份，它现在的身份是 Flyway 基线，不是设计文档——设计文档是 `02-数据库设计.md`（§B 首行已声明二者逐字段一致）。把基线放在 `docs/` 才是那个需要解释的状态。

**迁移时机：模块 01 建工程时一并做，本文档只出规划。** 现在迁会让 `check_consistency.py` 立刻失效（见 B2 第 21 项），而 `backend/` 目录此刻还不存在。

每个子域包内部固定这六个目录（**没有的就不建，不要建空目录**）：

| 目录 | 放什么 |
| --- | --- |
| `controller/` | HTTP 入口，只做参数绑定、调 Service、包 `R<T>` |

**关于 `com.edumatrix.org` 这个包名**：`org` 与 `org.springframework` / `org.slf4j` 的顶层包同名，看起来危险。实测无碍——Java 没有相对包解析，`import` 与完全限定名一律从根解析。在包 `com.edumatrix.org.node` 下同时写 `import org.w3c.dom.Node;` 与完全限定的 `org.w3c.dom.Document`，编译与运行均通过（实测于 `javac 11.0.31`；该解析规则在 17 上一致）。**记在这里是为了让下一个人不要"顺手改成 `organization`"**——改了就与契约 §6.2 的前缀对不上，URL 与包路径的互推关系断掉。

规范（契约 §7.3，此处只是把现有三个脚本已隐含的做法显式写下来）：

| 项 | 规定 |
| --- | --- |
| 命名 | `V{yyyyMMddHHmm}__{描述}.sql`。现有脚本用的是 **12 位**（`202608140000` = 日期 8 位 + 时分 4 位），新脚本沿用 |

| 幂等 | MySQL 不支持 `ADD COLUMN IF NOT EXISTS`，脚本内先查 `information_schema` 再决定 |
| 回滚说明 | 每个脚本配一段"怎么退"的注释，不要求可执行 down 脚本 |
| 大表 | `hw_answer_detail`（稳态约 3600 万行）与 `vod_heartbeat_log`（亿级）的变更按契约 §7.3 的四行对照表选方式；改列类型必须走 gh-ost 或 pt-online-schema-change |

## §E 公共层清单：只在模块 01 实现，其余模块只准 import

包名 `common` 而非某个领域名，是为了在**目录层面**就说明它不是第九个领域。下表逐项来自 `04-实施计划.md` 模块 01 的「对外产出（后续模块一律调用，不得自写）」。

| 类 / 构件 | 包 | 后续模块的正确用法 | 自己重写会怎样 |
| --- | --- | --- | --- |
| `TenantLineHandler` 实现类 | `common/tenant/` | 不碰。租户过滤由插件自动注入 | 业务代码里出现手写 `OR tenant_id = 0` —— 契约 §2.9 明令禁止，且模块 01 的自检项就是 grep 它 |
| `CurrentContextProvider`（SPI：`getTenantId` / `isSuperAdmin` / `getUserId` / `getNodeId`） | `common/tenant/` | **模块 02 注册一个实现 Bean 即覆盖默认的「无会话」实现**；其余模块不实现它 | 公共层反向依赖模块 02，或各处用未登记的会话键名字符串取租户 |
| `BaseEntity`（通用字段 + `@TableLogic`）、`TenantEntity`（+ `tenant_id`） | `common/entity/` | 35 张业务表继承 `TenantEntity`；`sys_tenant` / `sys_menu` 继承 `BaseEntity`；`sys_login_log` / `sys_oper_log` / `vod_play_auth_log` / `vod_heartbeat_log` **四张不继承**，字段自行声明（契约 §2.2 末尾的日志例外） | 逐表各写一份逻辑删除注解，早晚写歧；而给 `vod_heartbeat_log` 套上 `@TableLogic` 会注入 `AND deleted_at = 0` 而该列**根本不存在**，运行期 `Unknown column` |
| `TenantHelper.setTenantId / clear`、`runWithTenant(tenantId, Runnable)` | `common/tenant/` | 三类无会话入口一律用 `runWithTenant` 包住（契约 §2.8 规则 1） | 漏 `clear()` → 线程池复用 → 下一个任务串租户 |
| `SubtreeScopeHelper.subtreeNodeIds(myNodeId)` / `.assertInSubtree(targetNodeId)` | `common/subtree/` | 一切"我能看到哪些数据"的判定都调它 | 各模块自写子树查询 → 契约 §2.4 的三条执行路径变成 N 种写法，且极易退化成 `FIND_IN_SET`（慢查询即缺陷，契约 §7.1） |
| `NodeAncestorCache.get(nodeId)` / `.evictSubtree(nodeId)` | `common/subtree/` | 读祖先链一律走缓存 | 节点移动后缓存不失效 → 数据权限按旧树判定 |
| `R<T>`、`R.ok(data)` / `R.fail(ErrorCode)`、全局异常处理器 | `common/response/` | 所有 Controller 返回 `R<T>` | 响应体不符 `00-通用约定` §3，前端拆包逻辑对不上 |
| `PageResult<T>{total, list}` | `common/response/` | 所有分页接口返回它；`pageSize` 上限 100 由它强制 | `data` 里冒出第四个同级字段（§4.2 明令只有三者） |
| `ErrorCode` 枚举 | `common/errorcode/` | 只用枚举项，不写字面量 | 出现未在 `00-通用约定` §9 登记的码；C3 会抓，但代码里的字面量它看不到 |
| `IdWorker.nextId()` + Jackson `Long → String` 序列化器 | `common/id/` | 主键一律它生成；序列化器全局生效，不逐字段加注解 | 漏一个字段 → 前端精度丢失（`00-通用约定` §5） |

## §G 免登录白名单与拦截器注册位置

### G1 四条免登录接口与它们的处理位置

`00-通用约定` §2.3 的白名单共四条：

| 接口 | 身份来源 | 注册位置 |
| --- | --- | --- |
| `POST /api/v1/auth/login` | 请求体 | Sa-Token 拦截器排除路径 |
| `GET /api/v1/auth/captcha` | 无 | 同上 |
| `POST /api/v1/auth/refresh` | 请求体 refreshToken | 同上 |
| `GET /api/v1/vod/decrypt-key` | **URL 上的 `MtsHlsUriToken`** | 同上，但**处理方式与前三条完全不同**，见下 |

链路顺序：

```
① TraceIdFilter（Servlet Filter，最外层）
      ↓  免登录接口同样要有 traceId——密钥接口出问题时，没有它就无从定位
② Sa-Token 拦截器（SaInterceptor），排除上表四条路径
      ↓
③ Controller
      ↓
④ Service：MtsHlsUriToken 反查 studentId + lessonId → 跑与 8.1 逐条相同的 org_resource_grant 校验链
```

**`MtsHlsUriToken` 的校验不放在过滤器或拦截器里。** 三个理由：

1. 它同时是身份来源**和业务入参**，与 `GET /api/v1/vod/decrypt-key` 一一绑定，不是横切关注点；
2. `00-通用约定` §2.3 与模块 12 的禁止事项都要求它跑与播放凭证接口（`POST /api/v1/vod/play-auth`）**逐条相同**的授权校验链，而那条链在 Service 层（`PlayAuthChainService`）——拦截器够不着它，硬要够就会变成第二份校验逻辑，正是模块 12 明令禁止的；
3. 放进拦截器等于在 Sa-Token 之外再建一套鉴权入口。**免登录接口只有四条，其中三条不写业务表、第四条只读**（契约 §2.8）——这个面越小越好。

前端侧的对应事实：**该请求由 hls.js 内核发起，不经过 `frontend-h5/src/utils/request.ts`**。前端的 401 统一处理、traceId 展示、错误提示对它一律无效；取不到密钥表现为播放器错误事件，处置见 `03-03 §8.2` 与模块 14 规则 7。

### G2 `integration/` 与配置的对应关系

`integration/aliyun/` 里的四个 Client 是 §F4 第一类配置的**全部消费方**。这个对应是有意的：想知道"哪些配置是部署级的"，看这一个包的构造函数即可；反过来，任何业务包里出现 `@Value("${ALIYUN_...}")` 都是越界。

```
│                                              vodEventTaskScheduler 上）；调度中心登记 cron 0/10 * * * * ?

│                                              与 common/config/XxlJobConfig 互斥，靠 xxl.job.enabled 切换
└── worker/
    ├── StudentImportWorker.java       模块 17  从 org_import_task 取 tenant_id
    └── ExportTaskWorker.java          模块 17  从 stat_export_task 取 tenant_id
```

**为什么集中，而不是散在各自的业务包里**——四条理由，第一条是主要的：

1. **契约 §2.8 给这九个入口的是同一条规则**（显式取 `tenant_id` → `setTenantId` → 处理 → `clear()`，跨租户按租户分片，取不到一律拒绝并告警）。集中放置让这条规则可以**对着一个目录逐文件核对**；散开则要跨八个业务包 grep，而"漏了一个 Job 没包 `runWithTenant`"是**不报错的故障**——它安静地写进错误的租户。
2. **Job 是与 Controller 平级的入口**。Controller 有 URL 前缀作天然索引（契约 §6.2），Job 没有；`job/` 目录就是它的索引。
3. **有的 Job 天然跨领域**：`DailySettleJob` 读 `vod_watch_progress`、`hw_answer_sheet`、`hw_homework_target`、`hw_answer_detail`、`org_node`、`org_student` 等，写 `stat_*` 三表。放进 `vod` 是错的，放进 `homework` 也是错的，放进 `stat` 则掩盖了它对另两个领域的依赖。
4. **调度配置与代码要对得上**。XXL-Job 后台按 JobHandler 名注册，运维看到的是一张任务列表——代码侧有一张对应的目录列表，两边可以逐行核对。

**集中的边界（必须遵守，否则第 3 条会反噬）**：`Job` 类只做三件事——**取租户上下文、分片、调用领域 Service**。不写 SQL、不写业务判断、不注入 Mapper。业务逻辑仍然留在领域包里（`DailySettleJob` 调 `stat` 领域的结算 Service，后者再调 `vod` / `homework` 领域的只读 Service）。这样集中的只是**入口**，不是逻辑。

## §J 部署形态与多实例前置条件

> **放这里的理由**：不放 §A —— 那三条选型讲的是**代码怎么组织**（模块划分、包结构、前端工程数），
> 本节讲的是**进程怎么跑**，性质不同；不放 §F4 —— 那一节是**配置项的命名与分类**，
> 而本节的三条分别落在配置项、`pom.xml` 依赖、Job 路由**三处**，塞进配置表会让另外两条无处安放。
> 放在 §I 待决项之后：本节三条里有两条的状态就是「未定案」，紧邻着看最省跳转。
> **§I 不改字母**——`04-实施计划.md` §E 的 F-14 引用了「`05-工程结构.md` §I 的 `Q-1`」，
> 重排字母会把那个引用打断。

### J1 定案：单实例部署

**结论：当前定案为单实例部署。**

现在这么定的理由，三条都指向"最简写法此刻恰好也是正确写法"：

1. **一个开发者、每模块可能换 Agent**（§A1 的同一个前提）。多实例要处理的那些事——会话集中存储、任务路由、
   实例间一致性——每一条都要一次设计决策与一次验证，而它们在单实例下**一条都不需要**。
2. **K12 ToB 早期客户量**。契约 §6.1 的容量假设是每机构 1 万学生；`02-数据库设计.md` §6 的结论是
   单实例 MySQL 舒适区、无需分库分表。**数据层都还没到要拆的时候，应用层先拆没有收益。**
3. **单实例下最简写法即正确写法**：雪花 `worker-id` 取默认 0、定时任务直接跑、Sa-Token 会话放进程内存——
   三处都不需要额外装配。

**但这不是"暂时凑合"，而是一个带前置条件的定案：**

> **J2 那份清单没有全部处理完之前，不得部署第二个实例。**

这句话是本节存在的全部意义。三条风险的共同点是——**它们在单实例下全部正确、且测不出来**
（开发与测试环境永远是单实例），所以不会有任何一次构建、任何一个测试、任何一条告警来提醒你漏了它们。
唯一能防住的手段，就是在**动手加实例之前**有一处集中登记可查。

### J2 清单：改为多实例时必须同时处理

#### ① 雪花 `workerId`

| 项 | 内容 |
| --- | --- |
| **风险** | 多实例部署时 `SNOWFLAKE_WORKER_ID` 必须逐台不同 |
| **后果** | 两台配同一个号会产生**重复主键**，而重复主键**只在写入时报错、报的还是唯一键冲突，不会指向配置** |
| **处置** | 每个实例注入不同的 `SNOWFLAKE_WORKER_ID`（0~31） |
| **当前登记在哪** | **已登记**：§F4 部署级参数表 `SNOWFLAKE_WORKER_ID` / `SNOWFLAKE_DATACENTER_ID` 行，正文与理由都在那里，本节只引用不重复 |

#### ② Sa-Token 会话存储

| 项 | 内容 |
| --- | --- |
| **风险** | `backend/pom.xml` 只引 `sa-token-spring-boot3-starter`，**没有任何 `sa-token-redis-*`**，会话数据落在 `SaTokenDaoDefaultImpl`（**JVM 内存**） |
| **后果** | 三条，**完整论证见 `04-实施计划.md` §E 的 F-19，此处只作摘要**：① 跨实例 Token 互不认识 → 请求随机 401；② 应用重启即全员掉线；③ **PRD §7.3「登出/改密即时失效」静默失效**——用户在 A 机改密，A 机只踢得掉本机内存里的会话，**B 机内存里那份还在，旧 Token 继续有效**。<br>**第 ③ 条与①②不是一类**：①②表现为"登不上/掉线"，用户第一时间就会报；③**没有报错、没有任何指标会动**，只有被盗号的人事后知道 |
| **处置** | 改为集中式存储（`sa-token-redis-jackson` 或等价实现）。**这会新增依赖并改变部署形态，属设计决策，实现方不自行加**。<br>**即使不上多实例，也有一个重新评估的时机**：进程内存储意味着**每次发版全员掉线**。单实例下这不是安全问题，是**运维体验问题**——若发版频繁到让这件事变得难以忍受，那本身就是切换到集中式存储的充分理由，**不必等到加第二个实例**。 |
| **当前登记在哪** | **已定案：维持进程内存储**（`04-实施计划.md` §E 的 **F-19**）。理由：换 Redis 存储要新增依赖、加序列化配置、**多一个故障面**（Redis 挂 = 全员登不上），而收益在单实例下**是零**——该防的已由 §J1「J2 清单没处理完之前不得部署第二个实例」防住。<br>**本行的状态是「已定案维持现状」，不是「已处理」**：多实例前置条件依然成立，加第二个实例之前仍必须先改存储 |

#### ③ XXL-Job 任务路由策略

**风险**：当前所有定时任务未指定路由策略。多实例部署时，同一个任务会被**每个实例各触发一次**。

**后果按任务语义分四类**（任务清单与模块归属逐条核对自 `04-实施计划.md` §B，与本文 §H 的九个入口一致）：

| 任务 | 模块 | 多实例下重复触发的后果 |
| --- | --- | --- |
| 心跳落盘 `HeartbeatFlushJob`（Redis 脏集合 `vod:hb:dirty` → `vod_watch_progress`） | 13 | 两个实例读同一份脏集合，**学习时长可能被累加两次**；或一方落盘成功后移出脏集合、另一方读到空集，**该批次心跳静默丢失** |
| 日结算 `DailySettleJob`（`stat_student_daily` / `stat_teacher_daily` / `stat_node_daily`） | 16 | 同一天的统计行被算两遍；若用 `INSERT ... ON DUPLICATE KEY UPDATE` 累加则**数值翻倍**，若用覆盖写则只是浪费一次全量计算 |
| 转码事件消费 `VodEventConsumeJob`（SMQ 拉取） | 09 | **相对安全**——消息队列本身保证一条消息只被一个消费者取走，但两个消费者会争抢，且幂等键 `vod_file_id + EventType + Status` 已是必需项（契约 §2.8） |
| 授权巡检 `GrantConsistencyJob` | 11 | 重复执行本身幂等（只读巡检），**后果是资源浪费不是数据错误** |
| 脱敏任务 `AnonymizeArchivedStudentJob` | 07 | 同上（幂等更新：扫的是 `anonymized_at IS NULL`，脱敏后不再命中） |
| 作业截止 `HomeworkDeadlineJob` | 15 | 同上（扫的是到期未交的 0/1 答卷，置 4 后不再命中；并发同刻两实例固化的 `teacher_node_id` 是同一个值） |
| 敏感文件清理（**类名未定案**，本文 §H 暂记 `TempFileCleanupJob`，见 §I 的 `Q-2`） | 05 | 同上（物理删除已过期文件，第二次执行没有可删的） |
| 导出 Worker `ExportTaskWorker` | 17 | 产生**重复文件**，后果是资源浪费 |
| **导入 Worker `StudentImportWorker`** | 17 | **⚠ 这一条不能归进"资源浪费"**：两个实例若同时取到同一行 `org_import_task`，会**把同一批学生导入两遍**——那是数据错误不是浪费。后果取决于**取任务行的方式是否原子占位**，而模块 17 尚未落地，**该机制此刻还不存在**，故一并列为待确认 |

**处置**：多实例部署前，按任务逐个指定路由策略。

**`FIRST` 保证的是「同一次调度只发一台」，不保证「同一时刻只有一台在跑」**——调度中心从执行器列表里固定挑第一台，
所以单次触发确实不会重复；**但故障切换的瞬间不成立**：第一台假死时（进程还在、只是心跳超时被调度中心摘除），
下一次调度转派给第二台，而**第一台手上那批活可能仍在执行**——于是两台同时在处理同一份 `vod:hb:dirty` 脏集合，
或同时在算同一天的 `stat_*_daily`。

因此心跳落盘与日结算这类**有状态推进**的任务，`FIRST` 只是第一道，**仍须叠加分布式锁**，
或让落盘逻辑本身对重复执行免疫（**两者取其一，但不能只有 `FIRST`**）。
**写成「`FIRST` 或分布式锁」会让人以为二选一、做完 `FIRST` 就收工——那正好是只做了第一道。**

无状态的任务可用默认策略。**两个 Worker 另需明确任务行的原子占位方式**（见上表末行）。

**不要用「分片广播」**，除非任务本身按分片键做了切分——广播是让每个实例都跑一遍**不同的分片**，
而上述任务目前都没有分片逻辑，广播等于把重复触发变成必然。

**当前登记在哪**：**未定案**。多实例部署前须逐任务确认路由策略并在此登记。

### J3 维护约定：新的"只在单实例下成立"的实现，必须往 J2 里加一条

**将来任何一处"因为只有一个实例所以这样写没问题"的实现，都要在 J2 里补一行**，
写清风险 / 后果 / 处置 / 状态四栏。

**为什么这条约定值得单独写下来**：J2 现有三条的共同点是——**在单实例下全部正确，且没有任何自动化手段能发现它们**。
它们不是缺陷，所以测试不会红；不是慢查询，所以 §7.1 的指标不会动；不是命名或结构问题，
所以 `scripts/check_backend_conventions.sh` 的三条 grep 也抓不到。

**能防住它们的只有"有一处集中登记"这一件事。** 而集中登记只有在**每次都记**的前提下才有意义——
漏记一条，这份清单就从"部署前的检查表"退化成"部署前的部分检查表"，
而后者比没有更危险：它会让人以为查完了。
