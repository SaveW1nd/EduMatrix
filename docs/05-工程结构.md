# EduMatrix 工程结构（代码仓库的目录与包规划）

> **本文档定的是"代码放哪"，不定"代码做什么"。** 后者在 `04-实施计划.md`：17 个模块各自的表、接口、规则与验收标准。
>
> **文档权威顺序**（同 `04-实施计划.md` 首段）：`DESIGN-CONTRACT.md` > `03-API接口文档/` 六分册 > `01-PRD-产品需求文档.md` > `02-数据库设计.md` + 基线 DDL。本文档在这条链之下——**它不产生新的约束，只把已有约束落到目录上**。若本文与上述任一文档冲突，以上述为准。
>
> **为什么现在写**：仓库当前 19 个文件、0 行代码。一个开发者按 01 → 17 顺序推进，每个模块可能交给不同的 Agent 执行。没有统一目录约定，第 5 个模块和第 12 个模块会长成两种样子；而模块 01 交付的公共层被其余 16 个模块 import，**包路径定错一次就是全库替换**。

## §A 三个选型问题

### A1 单模块 Maven，不拆多模块

**结论：一个 `backend/pom.xml`，一个 `src/main/java`。**

参考仓库 RuoYi-Vue-Plus 是多模块，但那是**多人并行**的产物：module 边界在那里的作用是"你不能 import 我的内部类"，而这条约束只有在"你"和"我"是两个人时才需要机器来执行。

本项目的实际风险方向是**相反的**：

| | 多人协作项目 | 本项目（单人 + 单模块 Agent） |
| --- | --- | --- |
| 要防的事 | B 组乱 import A 组内部实现 | 模块 12 的 Agent **没看见**公共层，自己又写了一个子树查询 |
| 多模块的作用 | 有效——编译期就拦住 | **反向有害**——import 公共层需要先改 pom，摩擦越大越容易"就地再写一个" |

模块 01 的禁止事项已经明写「不重写公共层：后续模块需要上述能力时**调用这里的类**」。多模块把"调用"这件事变贵，正好和这条要求相抵。

**代价与处置**：单模块下没有编译期的分层护栏。处置不是引入构建工具，而是三条可 grep 的硬约束（同模块 01「做完什么算做完」的自检风格）：

```bash
# ① 业务包不得出现手写租户放行条件（模块 01 已有此项自检）
grep -rn "OR tenant_id = 0" backend/src/main/java --include=*.java        # 期望 0 行

# ② 业务 Mapper 不得出现 FIND_IN_SET（模块 01 已有此项自检）
grep -rn "FIND_IN_SET" backend/src/main/resources/mapper                  # 期望 0 行

# ③ 领域包不得互相 import（本文新增的约定）
grep -rnE "^import com\.edumatrix\.(org|course|vod|question|homework|stat)\." \
     backend/src/main/java/com/edumatrix/vod                              # 期望 0 行；八个领域各查一次
```

第三条是本文新增的**约定**，不是新约束——它只是把"领域之间通过 Service 接口交互、不互相摸实体"写成可执行的检查。跨领域读取一律走对方领域的 Service（例：模块 08 校验课时关联时读 `vod_video`，调 `vod` 领域的 Service，不直接注入 `VodVideoMapper`）。

**什么时候该拆**：出现第二个可独立部署的进程时（例如把 XXL-Job 执行器单独打包）。在那之前拆是提前支付成本。

### A2 按领域一级、分层二级

**结论：`com.edumatrix.<领域>.<子域>.{controller,service,mapper,entity,dto,vo}`。领域名 = 契约 §6.2 的八个路由前缀，一个不多一个不少。**

对比：

| | 分层一级（`controller/` 下放全部 Controller） | **领域一级（本方案）** |
| --- | --- | --- |
| Agent 拿到「做模块 07」的工单 | 要在 5 个顶层目录里各找一遍，改动散在 5 棵树 | 改动集中在 `org/member/` 一棵子树 |
| 两个模块同时落在同一层 | `service/` 目录混着 17 个模块的实现类 | 各自在自己的子域包里 |
| 从 URL 反推代码位置 | 推不出来 | `/api/v1/org/students/{id}` → `com.edumatrix.org.member` |

第三行是选它的主要理由：**契约 §6.2 已经把系统按领域切了一刀，这一刀是权威的**。让包结构与它同构，URL 与代码位置互相可推——这是 Agent 定位文件最省事的方式，也让「不自造领域名」这条纪律有了物理载体（想造新领域名，得先在契约 §6.2 加一行）。

**领域内为什么还要子域**：`/api/v1/org/**` 一个前缀承载 50 个接口、横跨模块 06/07/11/17。全部平铺在 `org/controller/` 下是 50 个类一个目录。子域按**名词**切（`node` / `member` / `grant` / `template` / `tag` / `dataimport`），不按模块编号切——模块编号是一次性的施工顺序，名词是长期的。

### A3 前端两个独立工程，不做 monorepo

**结论：`frontend-admin/`（PC 管理端 + 教师端）与 `frontend-h5/`（学生端），两个独立的 npm 工程，各自 `package.json`、各自构建、各自部署。**

页面归属（PRD §6.1 / §6.2 / §6.3）：A1–A22（管理端 22 页）+ B1–B13（教师端 13 页）落 `frontend-admin`；C1–C12（学生端 12 页）落 `frontend-h5`。

四条理由，按分量排序：

1. **依赖集完全不相交。** 管理端要 Element Plus（表格、树、表单、抽屉）；学生端 12 个页面里没有一个需要它，却要 DPlayer + hls.js（`frontend-admin` 只在媒资预览用得到播放器，且不需要禁快进与水印那套二开）。合成一个工程后，两边的依赖都会进对方的 `node_modules`，而**学生端恰好是最不能胖的那一端**——PRD §7.4 把微信内置浏览器（X5/XWEB）列为一级适配目标。
2. **PRD §7.5 第 5 条要求学生端能力可被小程序复用**（无 Cookie 依赖、无浏览器特有 API 依赖）。它是一个**将来要被整体搬走**的东西。与管理端共处一个工程，搬走时要先做拆分；独立工程时，搬走 = 换一层渲染。
3. **鉴权拓扑不同。** 管理端全部请求走 `Authorization: Bearer`；学生端除此之外还有一条**播放器内核发起、不带任何自定义头**的请求（`GET /api/v1/vod/decrypt-key`，00-通用约定 §2.3）。它不经过前端的 axios 实例，因此**前端的统一请求封装对它完全无效**——这条链路只存在于 `frontend-h5`，把它和管理端的请求层混在一起只会让人误以为拦截器能管到它。
4. **发布节奏不同。** 学生端 12 个页面基本由模块 14 一次做完；管理端 35 个页面从模块 03 铺到模块 17。合一个工程意味着模块 03 的一次改动要连带回归学生端构建。

**代价：请求封装会重复一份**（响应体 `{code,msg,data}` 拆包、业务错误统一 HTTP 200 的处理、bigint ID 字符串化、`X-Trace-Id` 回显——`00-通用约定` §3 / §5）。约 150 行。

**不为这 150 行引入 pnpm workspace**：workspace 的成本不是配置文件，是每次加依赖都要回答"装到哪个 package"——这与 A1 拒绝多模块 Maven 是同一笔账。代价的处置是**把重复的部分列清楚**，让它别悄悄分叉：

| 两端必须一致的东西 | 依据 |
| --- | --- |
| 响应体拆包与业务错误处理（HTTP 200 + `code`） | `00-通用约定` §3 / §3.3 |
| bigint ID 一律按字符串收发 | `00-通用约定` §5 |
| 时间格式与东八区 | `00-通用约定` §6、契约 §6.1 |
| `X-Trace-Id` 从响应头取出并在报错提示中展示 | 契约 §7.1 |

这四行改动时**两个工程都要改**——写在这里，是因为下一个人只会改他手上那一个。

## §B `docs/sql/` 的归属：选 A（全部迁走）

### B1 现状与三条路

当前 `docs/sql/` 混着两种身份的文件：

| 文件 | 身份 |
| --- | --- |
| `edumatrix_ddl.sql` | 41 张表全量 DDL，145 KB |
| `V202608140000__init_menu_and_role_menu.sql` | Flyway 增量脚本（`sys_menu` 124 行 / `sys_role_menu` 200 行） |
| `V202608140100__add_sys_menu_perms_unique.sql` | Flyway 增量脚本（`sys_menu` 加唯一索引） |

契约 §7.3 已经定了 `edumatrix_ddl.sql` 是 Flyway 初始基线 `V202608120000__baseline.sql`。**那个文件名目前不存在，这是将来时，不是缺陷。**

| 方案 | 判断 |
| --- | --- |
| **A 全部迁进 `db/migration/`，基线改名，`docs/sql/` 清空** | **选它** |
| B 留在 `docs/`，Flyway 用 `filesystem:` 指过去 | **不可行**。`filesystem:` 解析的是运行时工作目录下的真实路径，打成 jar 部署到服务器上 `docs/` 不存在，启动即失败。要规避只能把 `docs/` 一起打进发布包——那等于把 1.7 万行设计文档塞进生产制品 |
| C 基线留档 `docs/`、增量迁走 | **不可行**。同一份 DDL 存两处，一处被 Flyway 执行、一处被人阅读，**必然分叉**——而契约 §7.3 整节存在的理由就是防这件事（"该文件不再随手改动——否则新老环境会分叉"） |

**选 A 的正面理由**（不只是"另外两条不行"）：契约 §7.3 已经宣布这个文件**就是**基线。一个文件只有一个身份，它现在的身份是 Flyway 基线，不是设计文档——设计文档是 `02-数据库设计.md`（§B 首行已声明二者逐字段一致）。把基线放在 `docs/` 才是那个需要解释的状态。

**迁移时机：模块 01 建工程时一并做，本文档只出规划。** 现在迁会让 `check_consistency.py` 立刻失效（见 B2 第 20 项），而 `backend/` 目录此刻还不存在。

## §C 目录树

### C1 仓库根

```
EduMatrix/
├── README.md                  仓库导航（文档 + 工程入口）
├── .gitignore
├── docs/                      设计文档（现状不变，仅 sql/ 迁走，见 §B）
├── scripts/                   文档一致性检查（check_consistency.py + 说明）
├── references/                四个参考仓库的浅克隆与借鉴指引
├── backend/                   Java 服务（单模块 Maven）
├── frontend-admin/            PC 管理端 + 教师端（Vue 3 + Element Plus）
├── frontend-h5/               学生端 H5（Vue 3，无 Element Plus）
└── deploy/                    部署物：Dockerfile、compose、Nginx、环境变量样例
```

`references/` 内的四个仓库**只读源码学设计，不引入为依赖**。许可各异，其中 EduSoho 企培版协议限非商业用途，而本项目是 ToB SaaS 商用——**任何一行代码复制进 `backend/` 之前都要先看它的 LICENSE**。

包名 `common` 而非某个领域名，是为了在**目录层面**就说明它不是第九个领域。下表逐项来自 `04-实施计划.md` 模块 01 的「对外产出（后续模块一律调用，不得自写）」。

| 类 / 构件 | 包 | 后续模块的正确用法 | 自己重写会怎样 |
| --- | --- | --- | --- |
| `TenantLineHandler` 实现类 | `common/tenant/` | 不碰。租户过滤由插件自动注入 | 业务代码里出现手写 `OR tenant_id = 0` —— 契约 §2.9 明令禁止，且模块 01 的自检项就是 grep 它 |

| `ErrorCode` 枚举 | `common/errorcode/` | 只用枚举项，不写字面量 | 出现未在 `00-通用约定` §9 登记的码；C3 会抓，但代码里的字面量它看不到 |
| `IdWorker.nextId()` + Jackson `Long → String` 序列化器 | `common/id/` | 主键一律它生成；序列化器全局生效，不逐字段加注解 | 漏一个字段 → 前端精度丢失（`00-通用约定` §5） |

| `TraceIdFilter` + MDC + 线程池 / XXL-Job 继承包装 | `common/trace/` | 异步任务用包装后的线程池 | traceId 断在异步边界，出问题无法串起来（契约 §7.1） |

## §G 免登录白名单与拦截器注册位置

### G1 四条免登录接口与它们的处理位置

`00-通用约定` §2.3 的白名单共四条：

| 接口 | 身份来源 | 注册位置 |
| --- | --- | --- |
| `POST /api/v1/auth/login` | 请求体 | Sa-Token 拦截器排除路径 |
| `GET /api/v1/auth/captcha` | 无 | 同上 |
| `POST /api/v1/auth/refresh` | 请求体 refreshToken | 同上 |
| `GET /api/v1/vod/decrypt-key` | **URL 上的 `MtsHlsUriToken`** | 同上，但**处理方式与前三条完全不同**，见下 |

链路顺序：

```
① TraceIdFilter（Servlet Filter，最外层）
      ↓  免登录接口同样要有 traceId——密钥接口出问题时，没有它就无从定位
② Sa-Token 拦截器（SaInterceptor），排除上表四条路径
      ↓
③ Controller
      ↓
④ Service：MtsHlsUriToken 反查 studentId + lessonId → 跑与 8.1 逐条相同的 org_resource_grant 校验链
```

**`MtsHlsUriToken` 的校验不放在过滤器或拦截器里。** 三个理由：

1. 它同时是身份来源**和业务入参**，与 `GET /api/v1/vod/decrypt-key` 一一绑定，不是横切关注点；
2. `00-通用约定` §2.3 与模块 12 的禁止事项都要求它跑与播放凭证接口（`POST /api/v1/vod/play-auth`）**逐条相同**的授权校验链，而那条链在 Service 层（`PlayAuthChainService`）——拦截器够不着它，硬要够就会变成第二份校验逻辑，正是模块 12 明令禁止的；
3. 放进拦截器等于在 Sa-Token 之外再建一套鉴权入口。**免登录接口只有四条，其中三条不写业务表、第四条只读**（契约 §2.8）——这个面越小越好。

前端侧的对应事实：**该请求由 hls.js 内核发起，不经过 `frontend-h5/src/utils/request.ts`**。前端的 401 统一处理、traceId 展示、错误提示对它一律无效；取不到密钥表现为播放器错误事件，处置见 `03-03 §8.2` 与模块 14 规则 7。

### G2 `integration/` 与配置的对应关系

`integration/aliyun/` 里的四个 Client 是 §F4 第一类配置的**全部消费方**。这个对应是有意的：想知道"哪些配置是部署级的"，看这一个包的构造函数即可；反过来，任何业务包里出现 `@Value("${ALIYUN_...}")` 都是越界。

## §H XXL-Job 与 Worker 集中放在 `job/`

```
job/
├── VodEventConsumeJob.java            模块 09  10s 触发，单次拉取上限 16 条
├── HeartbeatFlushJob.java             模块 13  60s，批量落盘并判完播
├── DailySettleJob.java                模块 16  每日 00:30 结算 T-1
├── HomeworkDeadlineJob.java           模块 15  到期未交答卷置 status=4
├── GrantConsistencyJob.java           模块 11  每日低峰，按租户分批
├── AnonymizeArchivedStudentJob.java   模块 07  每日一次
├── TempFileCleanupJob.java            模块 05  敏感文件保留 7 天后物理清理（类名未定案，见 Q-2）
└── worker/
    ├── StudentImportWorker.java       模块 17  从 org_import_task 取 tenant_id
    └── ExportTaskWorker.java          模块 17  从 sys_export_task 取 tenant_id
```

**为什么集中，而不是散在各自的业务包里**——四条理由，第一条是主要的：

1. **契约 §2.8 给这九个入口的是同一条规则**（显式取 `tenant_id` → `setTenantId` → 处理 → `clear()`，跨租户按租户分片，取不到一律拒绝并告警）。集中放置让这条规则可以**对着一个目录逐文件核对**；散开则要跨八个业务包 grep，而"漏了一个 Job 没包 `runWithTenant`"是**不报错的故障**——它安静地写进错误的租户。
2. **Job 是与 Controller 平级的入口**。Controller 有 URL 前缀作天然索引（契约 §6.2），Job 没有；`job/` 目录就是它的索引。
3. **有的 Job 天然跨领域**：`DailySettleJob` 读 `vod_watch_progress`、`hw_answer_sheet`、`hw_homework_target`、`hw_answer_detail`、`org_node`、`org_student` 等，写 `stat_*` 三表。放进 `vod` 是错的，放进 `homework` 也是错的，放进 `stat` 则掩盖了它对另两个领域的依赖。
4. **调度配置与代码要对得上**。XXL-Job 后台按 JobHandler 名注册，运维看到的是一张任务列表——代码侧有一张对应的目录列表，两边可以逐行核对。

**集中的边界（必须遵守，否则第 3 条会反噬）**：`Job` 类只做三件事——**取租户上下文、分片、调用领域 Service**。不写 SQL、不写业务判断、不注入 Mapper。业务逻辑仍然留在领域包里（`DailySettleJob` 调 `stat` 领域的结算 Service，后者再调 `vod` / `homework` 领域的只读 Service）。这样集中的只是**入口**，不是逻辑。
