# 给模块 13/14 的实现结论

> 以下是本次踩出来的**实现级结论**，与"能不能播"无关，但**写代码时必踩**。
> 单独列出，是因为它们原本只存在于 POC 的 commit message 里，模块 13/14 的实现者不会去翻 git log。

## ① 全屏水印必须挂在 `fullscreenElement` 的子树内 —— 影响模块 14

原生 Fullscreen API 下，**全屏渲染层只包含进入全屏的那个元素及其后代**。水印若是 video 的兄弟节点，全屏期间画面上必然没有它。

实测：用原生控件的全屏按钮时，全屏元素是 `VIDEO` 本身，水印作为兄弟节点直接消失；改为对**播放器容器**全屏、并把水印挂进容器内部，水印才在全屏子树里。Aliplayer 的情况是——它把 `prism-player` 类直接加在传入的容器元素上、不另建根节点，所以水印挂在该容器内即可。

**判据是硬的，不必靠肉眼猜层级**：在 `fullscreenchange` 里判断

```js
el.contains(wm) === false   // → 全屏期间必然不可见，可直接判定
```

**但反向不成立**：`contains` 为真只排除了"没渲染"这一种可能，**压不压得住原生视频层仍需人眼确认**——视频可能被内核提升到独立的原生合成层，DOM 再高的 `z-index` 也压不上去。本次 ③ 正是靠人眼确认才判过。

**备选路径**：若原生全屏在某些内核（尤其 iOS）上保不住水印，可改用**不调用 Fullscreen API 的 CSS 全屏**——纯 CSS 铺满视口，页面仍留在普通文档流里，合成方式与内联一致，水印自然保留。

> 该做法在桌面 Chrome 上验证过：进入后 `document.fullscreenElement` 为 `null`、水印框与视口同尺寸。**真机未测**；Aliplayer 是否提供等价能力需另查，必要时可自行用 CSS 实现。

## ② `max_position` 的维护方式 —— 直接是模块 13 心跳规则的核心数据

**不能用 `timeupdate` 无条件抬高水位。** 拖动进度条时 `timeupdate` 会跟着手指一路触发，**在 `seeking` 判定之前**就把水位抬到目标位置，守卫回头一看"这地方早看过了"就放行。

实测代价：第一版守卫在 XWEB 上触发了 8 次拦截、**7 次最后仍落在前面**，还有一个会话**全程零拦截**（跳过 10 秒毫无阻碍）。

正确做法三条：

1. **只认连续播放造成的推进**——非 `seeking` 状态、且单次增量在合理区间内（实现用 `delta > 0 && delta < 1.5s`；1x 播放下一次 `timeupdate` 约推进 0.05~0.5s，拖拽跳变远大于此）
2. **去掉抑制窗口**——拉回后设一段"不再拦"的冷却期，会正好漏掉拖拽结束那一次 seek
3. **终判放在 `seeked`，不是 `seeking`**——`seeking` 里写回的 `currentTime` 赢不过还在进行中的原生拖拽，会被下一次拖拽立刻覆盖；**只有松手后的最后一次 `seeked` 才是用户真正的落点**，在那里再判一次并兜底拉回

修复后实测：16 次拦截，`seeked 落点`**每次都精确等于** `maxPosition`，全屏下同样拦得住，且后退与已看范围内跳转不误伤。

## ③ 播放器必须自绘控件 —— 这是"为什么不用原生 controls"的可验证理由

自绘控件的播放器会把所有 seek 入口收敛到一个函数上，包住它即可拦住全部入口。Aliplayer 的 `seek()` 即是；`references/DPlayer/` 里可以看到同一模式的完整形态——进度条松手、快捷键 ←/→、切集三个入口全部汇聚到 `player.seek(time)`，函数体里只有一行 `this.video.currentTime = time`（`src/js/player.js:194`、`controller.js:117-125`、`hotkey.js:30,38`），且**拖动过程只改进度条视觉、松手才提交一次 seek**。

量化对比：同一段拖拽操作，**原生 `<video controls>` 那条路要拦 14 次才夹住**（浏览器每约 65ms 下发一次 seek，写回不断被覆盖），**自绘控件只需 1 次**。

契约 §1 给出的理由是"保住播放器二开的三项前端能力"——**这一条比它更硬，因为可验证**：自绘控件把 N 次搏斗变成 1 次函数调用拦截。

## 方法论：对照实验里不要留下两个真值来源

`x5-video-player-type` 一度被两处写入：播放器配置写 `'h5'`（拉起 X5 自己的全屏播放器）、页面的 `applyVideoAttrs()` 写 `'h5-page'`（同层渲染、页面内联）。**同一个属性被给了两个互斥的值，最终以谁为准取决于写入时序**——而对照实验要的正是可比性，这会让对比失去意义。

处置：**统一到一处写**，并在 1 秒后把**实际生效**的属性读回来打进日志——

```
[ATTR] 1 秒后实际生效的属性 ["webkit-playsinline=true","x5-playsinline=true",
                             "x5-video-player-type=h5-page","x5-video-player-fullscreen=false"]
```

不靠"我设了所以它就是"。这个动作在所有对照实验里都值得保留。
